# ノイズ特性と検出限界（実測まとめ）

本機のノイズの正体と検出限界の記録。

**「要点」以降の確定値は device 0001（新潟県湯沢町・IIS3DHHC）のもの**で、2026-07 に
実イベント（福島県沖 20:53 / 令和8年熊本地震 16:27）周辺の静穏区間から切り分けた。
据え付けを変えた後の暫定測定は末尾の[測定ログ](#測定ログ暫定)に分けてある。**確定値の表は
本据え付け後の再測定を通すまで書き換えない。**

## 要点

- **ノイズフロアはほぼ白色 ~25-30 µg/√Hz**（全帯域で平坦）。broadband RMS ≈ **0.18 gal**（0-50Hz積分）。
- これは**センサ/電子系の熱雑音**であって環境振動（足音・生活振動）ではない。
  根拠: 静穏時PSDが平坦（白色）＝環境振動なら低周波へ急峻に立ち上がるはず。揺れの時間帯に
  人は動いていなかった観察とも整合。
- 例外は **z軸（垂直）のみ低周波 <0.2Hz で 90-130 µg/√Hz に突出**。重力を担う軸で
  傾斜・熱ドリフト・1/f 雑音が乗る。→ 遠地弱震では z を捨てて水平2軸が有利。

### 実測ASD（静穏時・z軸）

| 帯域 | ASD [µg/√Hz] |
|------|--------------|
| 0.5–1.5 Hz | 38 |
| 1–3 Hz | 33 |
| 5–10 Hz | 29 |
| 20–40 Hz | 28 |
| <0.2 Hz(z) | 90–130（垂直のみ突出） |

- データシート: IIS3DHHC = 45 µg/√Hz（±2.5g/16bit）。ファームは 1kHz 読み→10平均で 100Hz 化
  （`firmware/src/config.h` `kOversample=10`。帯域外を √10 で削減）→ 実効 in-band ~25-30 と整合。
- 量子化ノイズ（0.076 mg/LSB）は ~3 µg/√Hz で律速ではない。

## 連続震度での見え方（窓長の影響）

- 計測震度の移動窓は実機・tools とも **60秒**（気象庁準拠。`firmware/lib/Shindo/Shindo.h`
  `kWindowSamples`、`tools/jismo/realtime.py` `WINDOW_SECONDS`）。
- 60秒窓のベースライン ≈ 震度 **-0.55**。**5秒窓**にすると中央値 ≈ **-0.80**（過渡の居座りが
  消えて谷が深くなる）が、標準偏差は 0.100→0.128 と増える＝**フロア自体は下がらない**。
- 5秒窓は「静穏/イベントのコントラスト」向上には効くが、計測震度の定義から外れる。
  **検出用途には短窓連続震度より STA/LTA が筋がよい**（居座りもフロア悪化もなく短時間過渡を出す）。

## 他機との比較（同一地震・ほぼ同距離）

令和8年熊本地震（震央距離 東京・湯沢とも約 880km）:

| | 東京 ADXL355 | 湯沢 IIS3DHHC（本機） |
|---|---|---|
| 震度ベースライン | ≈ -1.2（≈0.085 gal） | ≈ -0.55（≈0.18 gal） |
| ノイズ密度(データシート) | ~25 µg/√Hz | 45 µg/√Hz |
| 熊本地震のバンプ | 震度0 まで +1.2階級（明瞭） | 連続震度では埋没 |

  （両者ほぼ同距離）。ADXL355 は低周波(1/f)特性も良く、遠地=低周波に二重に有利。

## 実務結論

- **現設置はセンサ律速**。遠地弱震を狙うなら順序は **①センサ更新（ADXL355級/速度計）→ ②設置改善
  （動線・空調から離す・基礎への剛結合・断熱）**。設置改善は現機材では二次的（フロアが白色＝センサ）。
- **現機材の繋ぎ**: 水平2軸（`detectlab.py --axes xy`）＋低帯域 STA/LTA。z軸の低周波ノイズを避けられ、
  遠地巨大地震の実体波(P)くらいは掠める。
- **長周期（遠地の表面波, <0.2Hz）は加速度計では原理的に不利**（a ∝ f²·D）。狙うなら速度計/広帯域
  地震計＋静穏・断熱設置が要る（詳細は会話ログ参照）。

## 再現

```bash
# ノイズASD（静穏区間のPSD）: welch で振幅スペクトル密度を出す（scratch スクリプト相当）
# 連続震度の窓比較: jismo.realtime.RealtimeIntensity(window_seconds=5 vs 60)
# 水平2軸検出: 
python tools/detectlab.py --csv <win>.csv --axes xy --band 0.5 2 --sta 2 --lta 60 --thr 2.8 \
    --eew "32.803,130.708,10,2026-07-28 16:27:18"
```

計測震度 ↔ 加速度: `I = 2·log10(a0) + 0.94`（a0 は 0.3秒累積超過の代表振幅）。

  ＝環境振動の混入ではない。

#### 何が分かったか

- **broadband RMS（特にy軸水平）は夜も昼も固定前の日々のばらつきを超えて下がった**
  （夜y: -20%・昼y: 固定前レンジの下限0.209を大きく割って0.177）。個々の日のノイズでは
  説明しにくい一貫した低下で、剛結による効果と見てよい。
- **in-band ASD（0.5–40Hz、電子系＋センサ熱雑音が支配的な帯域）はほぼ無風**（±1〜5%、
  固定前のばらつき範囲内）。[要点](#要点)の「フロアはセンサ律速」という結論と整合——
  設置を変えても電子系のノイズ密度そのものは変わらない。
- **z軸<0.2Hz（傾き・熱ドリフト）は device2 のような劇的な改善（92.9→27.9µg/√Hz）が
  出なかった**（81.8→80.8、無風）。device1はブレッドボード直挿しとはいえ元々机上に
  安定して置かれておりグラつきが少なかった可能性があり、device2の改善が主に
  「据え置きの不安定さの解消」由来だったとすれば、device1では同じ改善代がそもそも
  無かったと考えられる（未検証の仮説）。
- **日中の「鋭いピーク」(≥0.5gal・≥1.0gal)は固定前は毎日必ず何回か記録されていたのに、
  固定後2日は両日とも0回**。ユーザーが体感していた「生活振動で鋭いやつがかなり減った」は
  この時間帯・この指標では明瞭に裏付けられる。08-06の日中RMSが突出しているのは
  この日だけ突発的に強い活動があったためで、その日を除いても傾向は変わらない
  （08-07/08-08のpeaks≥0.5は0.88・0.63回/hで、固定後の0回/hより明確に多い）。
- **一方、夜間窓では逆に≥0.5gal・≥1.0galのピーク回数が固定前レンジの外側（多い方）に出た**
  （n=1なので単発の可能性が高いが、方向は日中と逆）。仮説として、剛結によりコンクリ
  ブロック～床経由の振動伝達がむしろ良くなり、日中は人の生活振動（ばね的な床のたわみで
  ある程度減衰していた歩行等）が減った一方、夜間は空調・冷蔵庫・給湯器等の機械振動が
  「素通し」で拾われるようになった可能性がある。**裏付けは無く推測**。固定後のデータが
  溜まったら夜間窓も複数晩に増やして再検証すること。
- **結論**: 「生活振動の鋭いやつが減った」という体感は、少なくとも日中については
  データが支持する。ただし固定後まだ2日ぶんしか無く、季節・曜日等の交絡は排除できていない。
  1週間程度データが溜まったら、この節を書き換えて確定版にすること。

#### 残るドリフト(z軸<0.2Hz)への対策候補（未着手）

上の通り、剛結で削れたのは主に**床のたわみ経由の生活振動**（設置場所の理屈は
[design.md §生活振動を受けにくい設置場所](design.md#生活振動を受けにくい設置場所)）で、
z軸<0.2Hzのドリフトはほぼ手つかずのまま残った。ドリフトの原因は2系統あり、
据え付けで削れるのは片方だけと考えられる。

1. **架台の熱膨張・傾き**（据え付けの剛性・熱容量で改善できる）— device2では
   ブロック固定でここが大きく効いた（92.9→27.9µg/√Hz）。device1で動かなかったのは、
   ブレッドボード直挿しとはいえ元々グラつきが少なく、この成分の伸びしろが
   そもそも小さかった可能性がある（上記・未検証の仮説）。
2. **センサチップ自体の温度係数(TCO)** — データシート上の仕様限界で、据え付けでは
   消せない。device1で残っているドリフトはこちらが支配的な可能性がある。

対策候補（優先度順）:

1. **断熱**（気流・温度勾配の遮断）。architecture上まだ未実施（§「2026-08-05
   コンクリートブロック固定後」参照、device2でも保留中）。(1)をさらに削れる可能性がある。
2. **温度ベースの補正**。2026-08-09に1号機の内蔵温度センサを有効化済み
   （[log/2026-08-09-iis3dhhc-embedded-temperature.md](log/2026-08-09-iis3dhhc-embedded-temperature.md)）
   なので、気温が一巡する数日〜1週間ぶんのz基線と温度の対応を取って補正式(TCO推定)を
   作れば、(2)をソフトウェアで打ち消せる可能性がある。未着手。
3. **センサ/アーキテクチャ変更**（速度計・広帯域地震計への切替）。<0.2Hzの長周期は
   `a ∝ f²・変位`という加速度計の原理的な不利と重なる領域なので、ドリフトを
   潰しきってもこの帯域を本気で狙うには限界がある。[実務結論](#実務結論)の通り、
   現状のプロジェクトの主目的（近傍〜中距離の実体波検知）には効かないため優先度は低い。

実害は主に**遠地・長周期の弱い地震のSNR悪化**（[実務結論](#実務結論)参照）。かつては
FFT版計測震度が巡回畳み込みの継ぎ目でドリフトに反応し誤検知する実害もあったが
（[intensity_pitfalls.md](intensity_pitfalls.md)）、線形デトレンドの追加で既に修正済み。
FIRのリアルタイム版はDCゲインを厳密ゼロに設計してあり巡回畳み込みでもないため、
同種の誤検知リスクは低いと考えられる（未検証）。
