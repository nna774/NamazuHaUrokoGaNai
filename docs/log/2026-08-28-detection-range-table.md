# 2026-08-28 「投げる価値があるか」の目安表を作った

これまでの事後解析10件（`0002-59595349`の完全埋没まで）で、マグニチュード×震源距離の
散布図をartifactとして作った際、ユーザーから「これはこの図の回帰係数を今後も事例が
増えるたびに更新する価値がある」「今高度利用者向けEEWが出た地震のうち"ありえそうな
もの"を投げてるが、これだと選び方が偏る」という指摘があった。

## 決めたこと

- **選び方の基準を「震源距離の固定の箱切り」ではなく「回帰予測に対する比率の帯」にする。**
  固定距離での足切りだと、境界から離れた「確実に捕れる/埋没する」事例をいくら増やしても
  回帰はほとんど動かない。回帰予測の0.8〜1.6倍のレンジ（過去の成功事例の実測/予測比が
  概ねこの帯に収まる）を「投げる価値あり」とし、レンジより近い（ほぼ確実に捕れる）ものは
  優先度を下げ、レンジより遠い（恐らく埋没）ものは埋没側の実例が手薄（10件中1件のみ）
  なので意図的に拾う価値がある、とした。
- **データはリポジトリを単一の真実にし、アーティファクトはそこから随時作る派生物にする。**
  アーティファクトのURLは会話をまたぐと忘れられるが、リポジトリならCLAUDE.mdの
  ドキュメント表から誰でも(未来のセッションの俺自身も)見つけられる。「事例が増えるたびに
  更新する」なら手計算よりスクリプト化が筋がいいとも判断した。

## 実装

- `tools/detection_events.csv`: 学習データ（id・日付・座標・深さ・M・判定・note・ログへの
  リンク）。**`id`列を追加した**——最初`name`（日本語の地名）をキーにしていたが、
  「by nameは脆い」という指摘を受けてスラッグ形式のidに直した。既存の`docs/log/`の
  ファイル名スラッグ（例: `ibaraki-m3.8`）と揃えられる時は揃えた。
- `tools/detection_range.py`: CSVから`log10(震源距離)=a+b*M`を回帰（verdict=good の
  事例のみ）し、マグニチュード別の目安レンジ表を出す。`--check <M> <km>`で候補地震の
  即判定、`--out-md`で`docs/detection_range.md`を再生成できる。距離計算は
  `detectlab.hypocentral_km`をそのまま import して使い、既存ログの数値との整合を保った
  （独自にhaversineで再実装すると数%ズレることを確認済み）。
- `tools/tests/test_detection_range.py`: 座標あり/なし両経路の距離計算、idの一意性、
  回帰の傾きの符号、`zone_of`の近すぎ/投げる価値あり/遠すぎの順序性を確認。
- `docs/detection_range.md`: 上記スクリプトの`--out-md`出力（**手編集しない**、
  事例追加時は再生成）。`docs/post_hoc_detection.md`に手順0.5として、
  CLAUDE.mdのドキュメント表にも1行追記して導線を作った。

## 現在の目安（2026-08-28時点、n=10・good=7）

`log10(震源距離) = 1.6175 + 0.1725*M`。M4.0で162〜325km、M6.0で359〜719kmが
「投げる価値あり」レンジ。詳細は[docs/detection_range.md](../detection_range.md)。

## 次にやること

- 高度利用者向けEEWが出た地震のうち、この表のレンジに入るものを機械的に拾って
  event数を増やす。特に埋没側（レンジより遠い）が10件中1件しかなく手薄。
- 事例を`detection_events.csv`に足したら`python tools/detection_range.py --out-md
  ../docs/detection_range.md`で再生成することを忘れないこと。
