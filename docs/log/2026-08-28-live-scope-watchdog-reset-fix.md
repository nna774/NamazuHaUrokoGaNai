# 2026-08-28 live_scope.pyで「放置すると0に張り付く」の原因はfirmware側の再起動ループと判断、hall_main.cppを修正

同日の[docs/log/2026-08-28-pendulum-mechanical-prototype.md](2026-08-28-pendulum-mechanical-prototype.md)で
「タイムスタンプ巻き戻りを検出したらバッファをリセットする」修正(コミット`98efe37`)を
入れたが、`tools/live_scope.py`で波形を眺めていると**放置している間に値が0に張り付き、
FFTも1000Hz(fs≈2kHzのナイキスト)まで出ているのに左端(DC近傍)にしか山が見えない**と
再度報告された。

## 原因: 98efe37は症状(巻き戻り後の壊れた表示)を直しただけで、再起動そのものは止めていない

`firmware/src/hall_main.cpp`の`loop()`は毎回無条件に`Serial.printf()`を呼ぶ。2kHz
(500us間隔)だとUSB CDCの送信バッファはすぐ埋まる——`live_scope.py`側の読み出しが
一瞬でも詰まる(GUIの再描画が重い、ウィンドウがバックグラウンドに回る等)と、
`Serial.printf()`はバッファに空きができるまで**ブロック**し、その間`loop()`が
止まってESP32のタスクウォッチドッグに落とされて再起動する——という因果は
前回のログで特定済みだった。

前回入れた修正はその**結果**(再起動でmicros()が0近くへ巻き戻り、fs推定と表示が
壊れたまま復帰しない)だけを取り除いた。しかし再起動の**引き金**(ブロッキング
`Serial.printf()`)自体は残っていたため、読み出しが詰まりやすい状況(まさに
「放置する」=誰も画面を操作せずウィンドウがバックグラウンドになりがちな状況)では
今も再起動が連続して起き続ける。バッファが数サンプル貯まる前に毎回リセットが
かかるため、波形パネルは実質空/直近の僅かなサンプルに張り付いたまま(見た目
「0に張り付く」)、FFTも有効なサンプル数が足りずDC近傍の短い過渡成分しか
見えない、という一貫した説明になる。

## 対処: ブロックせず、送れない時はサンプルを捨てる

`hall_main.cpp`の送信を「空きがあるかを`Serial.availableForWrite()`で先に確認し、
無ければ書かずに捨てる」方式に変更した。詰まった時に1サンプル欠けるだけで
`loop()`は止まらず、ウォッチドッグに落ちる経路そのものを塞げる。

```cpp
char line[40];
int len = snprintf(line, sizeof(line), "%lu,%d,%.4f\n", ...);
if (len > 0 && Serial.availableForWrite() >= len) {
  Serial.write(reinterpret_cast<const uint8_t*>(line), len);
}
```

`pio run -e hall-bringup` / `hall-bringup-c3` のビルド成功のみ確認済み。**実機での
再検証(実際に再起動が止まるか、`live_scope.py`側に「巻き戻りを検出」ログが
出なくなるか)はまだ**——このセッションは実機に手が届かないため未実施。

## もう一つの観察(FFTが左端しか見えない)についてはおそらく別問題

上記の再起動ループとは別に、**アームがまだ本固定されておらず質量-バネ系の
機械設計も未着手**という前提を思い出すと、そもそも今の仮組みでは明確な高速
リンギングがまだ出ていない([2026-08-28ログ](2026-08-28-pendulum-mechanical-prototype.md)に既述)。
FFTパネルのy軸は`spec[1:].max()`で線形スケール自動設定しているため、
強い低周波成分(手で振った時のゆっくりした揺れそのもの)が支配的だと、
仮に弱い高周波リンギングが実際に乗っていても線形スケールでは埋もれて見えない
——再起動ループとは独立に起こりうる、表示スケールの限界。ログスケール表示に
すれば弱い高周波成分も同時に見える可能性があるが、これは今回は未着手
(必要なら次回検討)。

## 追記: 実機で検証、再発を確認した上でノンブロッキング化版を焼き直した

上記の修正をコミットした直後、`/dev/cu.usbmodem101`に直接つないで検証した。

- **焼く前(旧firmware)の状態**: シリアルを開いたまま読み出しを2秒→4秒→8秒→60秒と
  段階的に止めてから一気に受信する、という形で「`live_scope.py`のGUI描画が
  詰まって読み出しが止まる」状況を模擬した。60秒放置してもその時点では
  リブートも巻き戻りも再現しなかった——が、この直後に**ユーザーが実際の
  `live_scope.py`画面を見たところ、改めて壊れているのを確認した**。単発の
  stallテストでは再現しないタイミング依存の不具合(GUIの再描画負荷そのものが
  詰まりを悪化させる等)である可能性が高いと判断し、原因の推定を変えずに
  修正を実機へ適用することにした。
- **`pio run -e hall-bringup-c3 -t upload --upload-port /dev/cu.usbmodem101`で
  ノンブロッキング化版を書き込んだ。** 起動直後の生データが健全(raw≈2312〜2319、
  タイムスタンプ差分から実測≈2000Hzと確認)なことを確認した上で、同じ60秒
  stallテストを再度実施——**ヘッダ再出力(リブートの兆候)・タイムスタンプ
  巻き戻りとも発生せず**。これで少なくとも「読み出しを止められている間、
  ボードは落ちない」という修正の効果は実機で確認できた。
- ただし**stallテストは`live_scope.py`のGUI自体を経由しない簡易な再現**であり、
  実際の画面を眺めながらの長時間放置での再発有無はまだ未確認。次に壊れた
  ように見えたら、まずこの版で直っているかどうかを確認すること。

## 追記: FFTパネルをlogスケールに変更

実機グラフ(ユーザー提供のスクリーンショット)で、低周波の大きな揺れが
線形スケールのy軸を支配し、それ以外の周波数帯が桁違いに潰れて見えない
状態を確認した。`tools/live_scope.py`のFFTパネルを`ax_fft.set_yscale("log")`に
変更し、y軸下限をその時点のピーク(`spec[1:].max()`)から4桁下に自動追従させる
形にした(スペクトルが全ゼロの時はlogスケールに矛盾するのでylim更新自体を
スキップし、直前の範囲を維持する)。matplotlib Aggバックエンドでのオフライン
検証のみ実施、実機の`live_scope.py`画面上での見た目確認はまだ。

## 追記: 単発ノイズ(analogReadの一瞬のディップ)にdespike(3点中央値)フィルタを追加

ユーザーがグラフを眺めていて「大きな流れとは別に、時々30〜50ポイント飛んで
1点だけのように見える」と報告。実機から直接8秒分(16642サンプル)取得して
調べたところ、`raw`値そのものに**ベースラインから20〜40カウントほど一瞬だけ
沈んで次のサンプルで即座に戻る**単発ディップが157件(頻度は不規則、8秒で157回)
乗っていることを確認した——`live_scope.py`側の表示バグではなく、ボードが
送ってくる`raw`の実値にノイズが乗っている。`hall_main.cpp`が`analogRead()`を
毎回1回呼ぶだけで平均化していないための、ESP32 SAR ADCの単発変換ノイズと
判断した(方向がほぼ一貫して負なのがランダム熱雑音というよりADC特有の
挙動に見える点も傍証)。

**wireフォーマット(`raw`)自体は変えず、`tools/live_scope.py`の表示側だけに
3点中央値フィルタ(`despike_median3`)を追加した。** 生データを削って
`hall_main.cpp`側でフィルタする案もあったが、「raw」という名前の意味を
保つのと、別の解析で生ノイズの実態を見たくなる可能性を残すため、表示専用の
後処理とした。合成データ(40Hz・振幅100の模擬共振+単発スパイク)でオフライン
検証: スパイク点の誤差が約1/3に減る一方、40Hz成分の振幅はほぼ無傷
(199755→199098、0.3%程度の差)。実機の`live_scope.py`画面上での見た目
確認はまだ。

## 追記: シリアル読み出しをGUI描画タイマーから切り離し、専用スレッド化

ユーザーから「pythonのwindowをバックグラウンドにして放置していると
おかしくなる気がする、読み出しレートが下がっているのでは」という指摘。
これはこれまでの一連の不具合の一次原因と整合する仮説だった——
`update()`(matplotlib `FuncAnimation`のコールバック)の中でシリアル読み出し
(`poll_serial()`)も行っていたため、**GUIの描画タイマー自体がmacOSの
App Nap等でスロットルされると、シリアル読み出しの頻度もそのまま落ちる**
という構造になっていた。読み出しが滞ればUSB CDC側にデータが溜まり、
(修正前は)firmwareのブロッキング送信が詰まって再起動する経路にも
つながっていた。

**シリアル読み出しを専用の別スレッド(`reader_thread`)に切り出し、GUIの
描画タイマーとは独立に回るようにした。** `update()`は`t_buf`/`v_buf`を
ロック越しにスナップショットして描画するだけになり、GUI側がどれだけ
詰まってもシリアル受信自体は止まらない。`t_buf`/`v_buf`への追記とスナップ
ショット取得の両方を`threading.Lock`で保護し、2つのdequeの長さが食い違う
（片方だけ追記された状態で読まれる）レースを防いだ。あわせて`Serial`の
`timeout`を`0`(非ブロッキング、GUIタイマー前提)から`0.2`(スレッド内で
ブロッキング待ちしてよい)に変更。

**検証**: matplotlibウィンドウを開かず、同じロック+スレッド構成だけを
実機に対して6秒動かし、"メインスレッドが何もしない(GUIが詰まっている状態)"
を模した。結果、読み出しスレッドは毎秒2100〜2650行前後を安定して蓄積し
続け、`t_buf`/`v_buf`の長さは常に一致・エラーも発生しなかった。
`live_scope.py`自体のGUIを介した見た目確認はまだ。

## 追記: `--window-seconds`をfft-secondsより長くするとリングバッファが足りず頭打ちになる不具合を修正

ユーザーが波形パネルをもっと長く見たいと`--window-seconds 20`を指定したところ、
x軸が-8秒相当までしか出ない現象を発見。原因はリングバッファのサイズ
(`maxlen`)が`args.fft_seconds`(既定4.0秒)だけを基準に`fft_seconds * 4000`
(実レート2000Hzに対し2倍の余裕を見込んだ想定)で決まっており、
`window_seconds`を考慮していなかったこと。既定のfft_seconds=4.0秒だと
実質バッファは約8秒分(4.0*4000samples÷実測2000Hz)しか保持できず、
window_secondsをそれより長く指定しても表示できるデータがそもそも
足りていなかった。`maxlen = max(window_seconds, fft_seconds) * 4000`に
修正し、大きい方の秒数が収まるようにした。

## 追記: `--log-file`で生データをCSV追記保存できるようにした

ユーザーが「錘が風で揺れている気がする、何もしなくてもこの程度は変動する」
という仮説を出した。ライブ画面のスクリーンショット1枚では「風だけの背景の
揺れ」と「手で加えた揺れ」を正確に比較できないため、`--log-file <path>`を
追加し、受信したCSVを生のまま(despike等の表示側の加工前)そのファイルに
追記保存できるようにした。セッションの境目が分かるよう開始時刻を
コメント行として書き込む。実機に対する簡易ハーネスで3秒分書き出し、
ヘッダ行・データ行とも正しく保存されることを確認した。

これで「しばらく何も触らずに記録→意図的に揺らして記録」を同じファイルに
残せるようになり、あとでオフラインに比較できる。実際にその比較をやるのは
次回。

## 追記: 波形パネルに経過時間(ボード基準)を表示

「揺らし始めた時間を見るため経過時間をどこかに出してほしい」という要望。
表示する秒数は`--log-file`のt_us(ボードの`micros()`起点、1列目)と
**同じ基準**にした——波形パネル右上に`t=123.4s`のようにその時点の最新
サンプルの`t_us/1e6`を表示するようにした。ホスト側の壁時計ではなくボード
基準にしたのは、ログファイルの1列目をそのまま検索できるようにするため
(壁時計にすると、ログと突き合わせる時にセッション開始時刻からの換算が
毎回要る)。「t=45.2sで揺らし始めた」とメモしておけば、`--log-file`の
出力を`t_us≈45200000`前後でそのまま検索できる。
