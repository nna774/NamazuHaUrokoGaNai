# 2026-08-28 live_scope.pyで「放置すると0に張り付く」の原因はfirmware側の再起動ループと判断、hall_main.cppを修正

同日の[docs/log/2026-08-28-pendulum-mechanical-prototype.md](2026-08-28-pendulum-mechanical-prototype.md)で
「タイムスタンプ巻き戻りを検出したらバッファをリセットする」修正(コミット`98efe37`)を
入れたが、`tools/live_scope.py`で波形を眺めていると**放置している間に値が0に張り付き、
FFTも1000Hz(fs≈2kHzのナイキスト)まで出ているのに左端(DC近傍)にしか山が見えない**と
再度報告された。

## 原因: 98efe37は症状(巻き戻り後の壊れた表示)を直しただけで、再起動そのものは止めていない

`firmware/src/hall_main.cpp`の`loop()`は毎回無条件に`Serial.printf()`を呼ぶ。2kHz
(500us間隔)だとUSB CDCの送信バッファはすぐ埋まる——`live_scope.py`側の読み出しが
一瞬でも詰まる(GUIの再描画が重い、ウィンドウがバックグラウンドに回る等)と、
`Serial.printf()`はバッファに空きができるまで**ブロック**し、その間`loop()`が
止まってESP32のタスクウォッチドッグに落とされて再起動する——という因果は
前回のログで特定済みだった。

前回入れた修正はその**結果**(再起動でmicros()が0近くへ巻き戻り、fs推定と表示が
壊れたまま復帰しない)だけを取り除いた。しかし再起動の**引き金**(ブロッキング
`Serial.printf()`)自体は残っていたため、読み出しが詰まりやすい状況(まさに
「放置する」=誰も画面を操作せずウィンドウがバックグラウンドになりがちな状況)では
今も再起動が連続して起き続ける。バッファが数サンプル貯まる前に毎回リセットが
かかるため、波形パネルは実質空/直近の僅かなサンプルに張り付いたまま(見た目
「0に張り付く」)、FFTも有効なサンプル数が足りずDC近傍の短い過渡成分しか
見えない、という一貫した説明になる。

## 対処: ブロックせず、送れない時はサンプルを捨てる

`hall_main.cpp`の送信を「空きがあるかを`Serial.availableForWrite()`で先に確認し、
無ければ書かずに捨てる」方式に変更した。詰まった時に1サンプル欠けるだけで
`loop()`は止まらず、ウォッチドッグに落ちる経路そのものを塞げる。

```cpp
char line[40];
int len = snprintf(line, sizeof(line), "%lu,%d,%.4f\n", ...);
if (len > 0 && Serial.availableForWrite() >= len) {
  Serial.write(reinterpret_cast<const uint8_t*>(line), len);
}
```

`pio run -e hall-bringup` / `hall-bringup-c3` のビルド成功のみ確認済み。**実機での
再検証(実際に再起動が止まるか、`live_scope.py`側に「巻き戻りを検出」ログが
出なくなるか)はまだ**——このセッションは実機に手が届かないため未実施。

## もう一つの観察(FFTが左端しか見えない)についてはおそらく別問題

上記の再起動ループとは別に、**アームがまだ本固定されておらず質量-バネ系の
機械設計も未着手**という前提を思い出すと、そもそも今の仮組みでは明確な高速
リンギングがまだ出ていない([2026-08-28ログ](2026-08-28-pendulum-mechanical-prototype.md)に既述)。
FFTパネルのy軸は`spec[1:].max()`で線形スケール自動設定しているため、
強い低周波成分(手で振った時のゆっくりした揺れそのもの)が支配的だと、
仮に弱い高周波リンギングが実際に乗っていても線形スケールでは埋もれて見えない
——再起動ループとは独立に起こりうる、表示スケールの限界。ログスケール表示に
すれば弱い高周波成分も同時に見える可能性があるが、これは今回は未着手
(必要なら次回検討)。
