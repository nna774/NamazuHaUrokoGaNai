# 2026-08-29 群馬県北部M3.2 事後解析 + store.load_windowのバッチ欠落バグ発見・修正

## きっかけ

ユーザーがNERV防災の揺れ検知通知を受け、ダッシュボードのライブ画面
（`#live?...&t=1787996919718786-1787996976301171&d=2`、18:48:39〜18:49:36 JST）で
波形に膨らみを見て「なんかある気がする」と調査依頼。

## 震源要素（tenki.jp）

- 発生: 2026-08-29 18:48頃、気象庁発表18:51
- 震源: 群馬県北部 N36.9/E139.3、ごく浅い、M3.2
- 震度1: 福島県檜枝岐村・群馬県沼田市（このほかの観測点なし）
- 観測点（湯沢町）からの震央距離43km・震源距離44km（`--eew`使用、深さは「ごく浅い」を5km仮定）

`/events?all=1&size=20`に該当時刻のイベントなし（直近は約19時間前の別イベント）。

## detectlab解析

標準設定（3軸1-10Hz）、`--eew "36.9,139.3,5,2026-08-29 18:48:48"`（発生秒は未公表のため、
観測されたS波到達から逆算——後述）:

| 項目 | device1 | device2 |
|---|---|---|
| STA/LTA peak | 12.23 | 15.46 |
| onset候補 | 18:48:58.34 | 18:49:00.07 |
| S窓(18:48:57-19:49:00) SNR | 3.23 | 2.29 |
| S窓 直線性 | 0.58 | 0.59 |

両機のonsetは0.2秒差でほぼ同時、STA/LTAは閾値4を大きく超過。S窓のSNRは明確に背景を
上回るが、直線性が判定基準の0.6にわずかに届かず`classify_snr_wrect()`は「要検討」止まり。
P窓・コーダ想定域は「微妙」。総合判定は**「要検討寄りのprobable」**——2機が独立に同時刻へ
反応した点は強い根拠だが、直線性の閾値超過は明確ではない小さな揺れ、というのが実態。

### 発生時刻の秒をS波到達から逆算した

JMA発表は分単位（18:48頃）。距離44km・`S_VEL_RANGE=(4.5,3.5)`からS波到達は発生+9.8〜12.6秒。
観測されたonset(18:48:58〜19:49:00)がS波だと仮定すると発生時刻は18:48:47〜18:48:50付近と
推定でき、「18:48頃」と矛盾しない。この逆算値(18:48:48)を`--eew`に使うことでP/S窓が
実際の過渡と整合する解析になった（発生時刻を18:48:00と置いた最初の試行ではP/S窓が
過渡より50秒以上前にずれて出た）。

## JMA計測震度換算では自動確定に届かない

`lambda/common/detect_core.analyze()`と同じ計算（`jma_fft.filtered_composite` →
`core_slice`で端5秒除去 → 閾値0.5相当=0.60galが0.3秒継続で確定）を実データで直接回したところ:

- device2, 2026-08-29 18:48:51.575064 終端・120秒窓: **comp max = 0.35gal**（閾値0.60gal未達、
  above-threshold区間なし）

STA/LTAは大きく閾値超過していても、JMA計測震度としては震度0相当で自動確定の閾値に
届かない——小さく近い揺れが「STA/LTAでは目立つがJMA震度では小さい」典型例。

## 副産物: `store.load_window`のバッチ欠落バグを発見・修正

上記の解析中、3分窓のdetectlab重ね描きでdevice2のonsetが18:48:21と、device1・単体窓
解析(18:49:00)と37秒もズレて出た。原因は`lambda/common/store.py`の`load_window`/
`load_event`が、同一デバイスの生バッチを実時間の欠落を考慮せず`np.concatenate`していた
こと。device2の生バッチを直接確認したところ、18:46:58.67〜18:47:35.82に**37.1秒の
完全な欠落**があり、窓がこれをまたぐと欠落後のサンプルの時刻(`win_start + i/fs`)が
実時刻より欠落秒数ぶん早く計算されていた。

**修正**: `_concat_batches_dropping_leading_gaps()`を新設し、バッチ間隔が
`BATCH_GAP_TOLERANCE_US`(2秒、正常な送信ジッタの実測上限0.1-0.4秒に対し十分な余裕)を
超えたら、そこより前を捨てて欠落後の連続区間だけを返すようにした（`load_window`・
`load_event`共通）。欠落を跨いで繋ぐより、短くても時刻が正しい区間を返す方を選んだ——
JMA-FFTフィルタは巡回畳み込みなので、欠落を跨いだ継ぎ目は窓の**内部**にリンギングを
持ち込みうる（`detect_core.py`のコメント参照）。`lambda/tests/test_store.py`にバッチ間
欠落のテストを追加、`pytest lambda/tests`は159件通過。

**このバグが今回の見逃しの原因ではないと確認した**: 修正前後で同じ120秒窓の
comp maxを計算し直したところ、修正前0.3517gal・修正後0.3515galとほぼ同値
（この窓ではたまたま欠落が窓の範囲外だった）。今回の未確定は上記のとおり
単純にJMA計測震度が閾値未達だったため。ただし窓が欠落を跨ぐ組み合わせは
一般には起こりうるので、修正自体には意味がある（特に閾値ギリギリのイベントで
リンギングが判定を左右しうる）。

## device2の周期的な約37秒欠落は現在も継続中・原因はTASK_WDT

生バッチの連続性を18:00〜19:08 JSTの範囲で確認したところ、37秒前後（1回だけ80秒）の
完全欠落が3〜13分おきに不規則に繰り返し発生していた。調査時点（19:02台・19:07台）でも
継続して発生していることを確認。ユーザーが並行して調べた結果、**原因はESP32の
TASK_WDT（タスクウォッチドッグタイマ）**と判明。ファーム側の対応はユーザーが別セッションで
継続する。`docs/adxl355.md`§5.1.1に2026-08-03の「数分の完全欠測ギャップ、再起動/再接続と
見られる」という記述があるが、それは分単位の話で規模が違う——今回のような数十秒・
数分〜十数分おきの頻発パターンは未記載だったため、`docs/adxl355.md`に追記した。
