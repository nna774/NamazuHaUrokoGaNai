# device1の新しい再起動を調べ、WDT panic説にたどり着く

PR #36（TLS証明書ピン留め）をマージした直後、ユーザーから「マージ直前にdevice1がまた
再起動していた、直後に家のインターネット不調のアラートが来たので関係ありそう」と
指摘があり調査した。

## 観測事実

- `/devices`とDynamoDB `namazu-devices`を確認: device1の`boot_epoch_us`が
  **2026-08-08T10:10:44 JST**に更新されていた（＝この時刻に再起動）。`fw_version`は
  `c891e89`（v1.7.0、PR #36のv1.8.0はまだOTA配信していない）のままで、**この再起動は
  PR #36のマージやOTA配信とは無関係**
- 同時刻、device2の最終受信(`last_ingest_at_us`)が**10:10:59 JST**で止まっており、
  以後(調査時点の10:17時点で)オフライン状態だった。device2自身の`boot_epoch_us`は
  更新されておらず（＝再起動はしていない、単に通信が止まっているだけ）
- watchdog Lambda(5分おきEventBridge)のCloudWatch Logsを確認: 直近の実行は
  いずれも短時間(130〜150ms)で終わっており、Slack通知は送られていない
  （オフライン判定の300秒しきい値に達したのが10:15:59、次のwatchdog実行は
  10:19:20頃の見込みで、調査時点ではまだ発火前だった）→ ユーザーが受け取った
  「インターネット不調のアラート」はNamazuのSlack通知ではなく、ルーター/ISP側の
  通知だったと考えられる

device1の再起動とdevice2の受信停止がほぼ同時刻という一致から、家庭内ネットの瞬断が
両機に同時に影響したという筋は堅い。ただし「なぜdevice1は再起動し、device2は
（この時点では）再起動せず単に止まっただけなのか」という機構は分かっていなかった。

## コードを読んで見つけた新しい仮説

`firmware/src/main.cpp`の`uploaderTask`は`esp_task_wdt_config_t`で**10秒・
`trigger_panic = true`**のtask watchdogに登録されている。`gUploader->pump()`が
返った直後にしか`esp_task_wdt_reset()`を呼んでいない。

一方`WiFiClientSecure`(`~/.platformio/.../WiFiClientSecure/src/WiFiClientSecure.cpp`)は
`handshake_timeout = 120000`（120秒）をデフォルトで持っており、TLSハンドシェイクの
待ちループ(`ssl_client.cpp`)はこの120秒に達するまで独自に粘る。このループの中で
`esp_task_wdt_reset()`は一度も呼ばれない（呼べるのはアプリ側のコードで、ライブラリの
奥のこのループには手が届かない）。

つまり、ネット瞬断でTLSハンドシェイクが詰まると、ライブラリは120秒粘ろうとするが、
**その前に10秒でESP-IDF側のtask watchdogが先に発火し、`trigger_panic=true`により
強制パニック再起動する**。パニックハンドラは`flushToSpill()`を経由しないため、
RAM上に溜まっていたバッチは毎回失われる。

これが正しければ、2026-08-08 10:10のdevice1再起動は「ハンドシェイクがWDTより先に
詰まって単発でpanic→再起動→再接続後は正常に戻った」ケースとして説明がつく。
さらに、[2026-08-07 22:04の70分間ゼロ退避](2026-08-08-device1-outage-and-deploy-drift.md)も
単発のフリーズではなく「詰まる→10秒でpanic→再起動→WiFi再接続→また詰まる→panic……」
の再起動ループが続いていた、という解釈で説明できる可能性がある。

## 未検証

- この仮説は**コードリーディングと1件のタイムスタンプ一致からの推論**であり、実機での
  裏付けは取っていない
- `esp_reset_reason()`（未実装、`docs/design.md`未定事項）があればパニックかどうか
  直接判別できた
- [heapテレメトリ](2026-08-08-heap-telemetry.md)（PR #37）が配信済みであれば、この
  再起動直前にheapが健全だったか断片化していたかで、このWDT panic説と「バックフィル
  起因のヒープ枯渇」説（`docs/design.md`の別項目）を切り分けられたはずだった。
  **どちらもまだ実機配信前で、今回は間に合わなかった**

## 次に何が可能になったか

`docs/design.md`「送信の信頼性」の未定事項に新しい仮説として記録した。次に同種の
再起動が起きた時、`esp_reset_reason()`とheapテレメトリの両方が配信済みであれば、
この場でどちらの説（あるいは両方、あるいはどちらでもない別の原因）かを実機データで
判別できる状態に近づいた。対策の実装はまだ着手していない（例: TLSハンドシェイクの
タイムアウトをWDTの10秒より短く設定してライブラリ側に優雅に失敗させる、WDTを少し
伸ばしつつハンドシェイク前後でresetを稼ぐ、等が候補になりそう）。
