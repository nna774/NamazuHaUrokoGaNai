# 2026-08-07夜の家庭内ネット障害でdevice1が長時間欠測した件を調査する

2026-08-07 22:00頃、自宅のインターネットが落ちてdevice1が欠測した。通知から約70分後、
ユーザーが手動で電源を抜き差しするまで復帰しなかった。「通知にreplyが付いていない」
「device2は自動復帰したのにdevice1はしなかった」「ダッシュボードを見るとログはある
ように見える」の3点を実データから調査した。**実装は無し、調査のみ**（副産物として
本番のデプロイ漏れを1件直した）。

## 何が分かったか

### 1. 欠測・復帰の実測タイムライン

S3の`raw/`キー（測定開始時刻ベース）とアップロード時刻(LastModified)を突き合わせて
時系列を復元した。

- **device1**: 最終データ21:59:03 JST → 欠測通知22:04 → ユーザーが手動で電源抜き差し
  → 23:08:31再起動 → 実データ再開23:09:07（**バックフィル無し、約70分ぶんが消失**）
  → 復帰通知23:14
- **device2**: 最終データ21:58:58 JST → 欠測通知22:09 → WiFi再接続・バックフィル開始
  22:15:04 → 復帰通知22:19 → **バックフィル最中の22:13:39〜22:18:57（約5分18秒）に、
  誰も触っていないのにもう一度測定が止まっている**（`boot_epoch_us`の再計算結果とも
  整合。docs/uptime.md参照）

アップロード時刻だけを見ると「バックフィルで埋まっている」ように誤認する
（device2のケース）。**キー内timestampと実アップロード時刻を突き合わせて初めて
2件目の穴が見えた。**

device2の再クラッシュの原因は未特定だが、バックフィルは通常30秒間隔のところを
数秒おきにTLSハンドシェイクを連発するため、ヒープを圧迫した可能性が高い
（`batch-uplink/src/Uploader.cpp`の`postBatch()`のコメントで既知のリスクとして
警告されていた内容と符合する）。

### 2. Slack通知に個人メンションが付いていなかった理由

`lambda/watchdog/handler.py`へのメンション追加（コミット`8fba024`、2026-08-04）は
**一度もoriginにpushされないままローカルにだけ存在していた**。本番のwatchdog Lambdaは
それより前のビルドのまま更新されずに今回の障害を迎えた——欠測/復帰の判定ロジック
自体は正しく動いていたが、メンション無しで投稿されていた。デプロイ済みLambdaを
AWSから直接取得してハッシュ比較し確認した。

### 3. ローカルmasterとoriginの乖離

調査の過程で、ローカルmasterがorigin/masterと32コミット分乖離していると判明した
（稼働時間/再起動検知機能・温度トレンド等がローカル未反映）。`git merge
origin/master`（コンフリクト無し）→ push → `build_lambda.sh` + `terraform apply`で
本番4Lambda（ingest/api/detect/watchdog）を再ビルド・再デプロイし、デプロイ済み
コードが現在のmasterと完全一致することを確認した。

## なぜバックフィル無しで70分丸ごと消えたか

`Uploader::enqueue()`はRAMキュー（`kMaxRamBatches`: device1=6本/3分、device2=3本/
45秒）を超えた時だけ自動でLittleFSへ退避する。`uploaderTask`のループ構造上、
WiFi接続待ちだけなら`connectWifi()`が20秒で必ず一度リターンし、その後キューの
吸い出し処理まで到達するはずなので、**device1が70分間1本も退避できなかったのは
単なるWiFi未接続ではなく、タスク（あるいはチップ全体）がどこかで完全にフリーズ
していたと考えるのが自然**。ユーザーが電源を抜き差しした時点で追加的に失われたのは、
直近最大3分（RAM分）程度と見られる。

## 次に考えないといけないこと（未着手・別セッションで設計から相談する）

- **`esp_reset_reason()`を次バッチのヘッダ等で報告する。** 「パニックで落ちたのか・
  電源断か・ブラウンアウトか」を区別できないと、今回のような調査を毎回手作業で
  やる羽目になる
- **クラッシュ直前にRAMキューをLittleFSへ退避する経路を作る。** 現状
  `flushToSpill()`はOTA直前にしか呼ばれない。パニックハンドラやtask watchdogの
  フックに仕込めないか検討する
- **物理ボタン長押しで手動`flushToSpill()`を叩けるようにする。** ただし
  「uploaderTaskがまだ生きていて特定の待ちで固まっているだけ」の場合しか救えない
  ——チップごとフリーズしていたら割り込みのハンドラすら実行されない可能性がある、
  という限界を理解した上で設計する（ISRから直接LittleFSを叩くのは危険なので、
  フラグを立てて別経路で拾う形になるはず）
- **バックフィル中のクラッシュ（device2で今回発見）の原因調査。** TLS
  ハンドシェイクの連続実行によるヒープ圧迫が疑わしいが未検証。バックフィル送信に
  バックオフ/間隔を入れるなどの対策が要るかもしれない

## 次に何が可能になったか

watchdogの欠測/復帰通知に個人メンションが再び付くようになった。ローカル/origin/
本番の3者が一致した状態に戻ったので、今後の作業はこのズレを気にせず進められる。
device1のWiFi無応答対策は上記の未定事項として次回に持ち越し。
