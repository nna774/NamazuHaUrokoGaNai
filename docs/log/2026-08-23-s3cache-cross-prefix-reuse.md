# s3cacheでraw/⇔events/を相互流用する

## 何を決めたか

`tools/s3cache.py`の`CachedS3.get_object`に、raw/とevents/を跨いだキャッシュ流用を
追加した。片方のキーが未キャッシュでも、もう片方（対になるキー）が既にキャッシュ
済みならそちらのバイト列をそのまま使い、S3へは通さない。

判定はキー末尾の`<batch_start_us:020d>.bin`（`lambda/common/s3util.py`の`raw_key`/
`event_batch_key`で共通の書式）が一致するかどうかだけで行う。一致すれば中身は
`common.store.copy_raw_to_event`が検知時に`copy_object`でrawをそのままコピーした
ものなので、バイト単位で同一と分かっている。複数ヒット（同一マイクロ秒に複数
デバイスがバッチを開始、原理上ほぼ起き得ない）した場合はどれが正しいか決められない
ため諦めて本物のGETに落とす。

## なぜそう決めたか

`detectlab.py`等での解析セッションは、rawを読んでから該当イベントの確定波形だけ
見たい、逆に大量にrawを読み込んだ後にeventの範囲だけ描画したい、という行き来が
よく起きる。従来のs3cacheはキーをそのままミラーするだけなので、この行き来のたびに
（中身は同じでも）別キーとして毎回S3へGETし直していた。

コスト自体はS3のGET料金として見ればほぼ無視できる額だが、対話的な解析中の
レイテンシとしては地味に乗る。キー末尾の書式が固定でraw/events間の対応が
機械的に取れることが分かっていたので、s3cache側だけで完結する軽い変更で
このレイテンシを消せると判断した。

## 副作用・注意点

- ディスクの重複は解消しない（両方のキーパスにそれぞれ実体を書く）。1バッチは
  ヘッダ32B+int16×3軸×3000サンプル≈18KB程度で、イベントコピー対象は数バッチ
  程度のため、重複分のディスク使用量は無視できる規模と判断しシンプルさを優先した
  （symlink化などは見送り）。
- `list_objects_v2`は従来通り毎回本物のS3へ通す。今回変えたのは`get_object`だけ。
- テストは`tools/tests/test_s3cache.py`に新規追加（4件: events側の再利用・raw側の
  再利用・キャッシュ無しでのフォールバック・複数ヒット時のフォールバック）。
