# ダッシュボードの既定表示機を2号機にした

## 何を決めたか

ダッシュボードをURLハッシュ無しで開いた時のライブ波形の既定機を、従来の「実在デバイスの最若番」（実質1号機）から2号機へ変更した。

## なぜ

ユーザーの希望。単に既定値を`'2'`に固定するのではなく、`dashboard/app.js`の`fillLiveDevices()`にある既存の「URL由来の選択が実在しなければ最若番へ倒す」フォールバック（デバイスを外した後のURL対策）を壊さないよう、「未選択（URLに`d`も無く、UIでの手動選択も無い）」ケースだけを新設の`DEFAULT_LIVE_DEVICE_ID = '2'`に向け、それ以外（無効な`d`指定など）は従来通り最若番へ倒す形にした。2号機が存在しない場合も最若番へフォールバックする。

## 何が変わったか

- `dashboard/app.js`: `liveDeviceId`の初期値`null`と`DEFAULT_LIVE_DEVICE_ID`定数を追加。`fillLiveDevices()`のフォールバック分岐を「未選択時は既定機優先、それ以外は最若番」に変更。

動作確認は`python3 -m http.server`で`dashboard/`をローカル配信し、ブラウザで本番API
(`https://api.namazu.dark-kuins.net`、読み取り専用)相手に
(1) ハッシュ無し初回ロードで2号機が選ばれる、(2) `#`のみでも同様、(3) UIで1号機を手動選択後「ライブに戻る」を押しても1号機のまま保たれる、の3点を確認した。

サーバ側`lambda/api/handler.py`の`_resolve_device()`（`?device=`無指定時に最若番を返す、`/devices`取得自体が失敗した時のみ通る経路）は今回変更していない——今回の要望はダッシュボードの通常起動時の既定表示に限定されるため。

## 次に何が可能になったか

デプロイ手順（`CLAUDE.md`のデプロイ手順節）に沿ってS3 syncとCloudFront invalidationをすれば本番へ反映できる。
