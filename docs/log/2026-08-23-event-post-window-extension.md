# イベント保存窓のPOST_SECONDSを90秒→600秒へ引き上げる

## 背景

[2026-08-23のM5.9事後解析](2026-08-23-ibaraki-nanbu-m5.9-post-hoc-detection.md)で追加した
`detectlab.py`の直線性一致度パネルにより、STA/LTAが検知閾値を割った後もdevice1/2間の
コヒーレンスは2分近く高いまま残り、地震前と同じ無相関の乱高下に戻るまで発生から
約190秒かかると分かった。「検知窓（閾値超過）より実際に揺れていた時間の方が長い」。

3.11のように強い揺れが分単位で続くケースでは、`lambda/detect/handler.py`の
`_copy_event_waveforms`が保存する範囲（`onset`基準に`PRE_SECONDS=30`/
`POST_SECONDS=90`固定）が実際の揺れの長さに対して不十分ではないか、という懸念から
見直した。

## 現状の仕組みの再確認

`_copy_event_waveforms`は固定窓だが、揺れが閾値(震度0.5相当)を継続して超えている間は
`_confirm()`がstrideごとに再発火し、そのたびに窓がスライドして追加コピーされる
（`s3.copy_object`は追記であり削除されないため）。実データ（`0001-59580602`）で
確認したところ、実際の保存範囲はonsetから-158秒〜+84秒、約240秒分に達しており、
単純な120秒固定窓より広かった——再発火による延長は実際に効いている。

ただし今回のケースでは+84秒止まりで、コヒーレンスが残っていた+190秒には届いていない。
再発火の条件が検知そのものと同じ**閾値超過**なので、振幅が閾値を最終的に下回れば
（たとえ物理的にまだ揺れていても）再発火が止まり、それ以上は伸びない。

## 決定

`POST_SECONDS`を90秒→**600秒（10分）**に引き上げる。1回のトリガーだけで
10分先まで保存できるようにし、再発火に頼らずとも3.11規模の長時間振動を
十分カバーできる安全マージンを持たせる。

**`last_us`（セッションの最終活動時刻）を使った動的な窓アンカーは見送った。**
検討はしたが、`det.onset_us`は揺れが続く限りstrideごとに前進していくため
`last_us`とほぼ一致し、`POST_SECONDS`を十分大きくした今、両者の差はほとんど
意味を持たない。複雑さに見合うメリットが薄いと判断し、フラットな定数だけで
済ませた。

## 副作用・関連する別問題

- `_preserve_prompt_waveforms`（速報のみで終わったイベントの確定判定待ち時間）も
  同じ`POST_SECONDS`を使っているため、未確定速報の`checked`確定までの待ち時間も
  最大10分に伸びる。実害は無い（1時間より古い分は別途諦めるガードが既にある）。
- S3の`copy_object`呼び出し回数が増える（1回の窓が広がるぶん対象バッチ数が増える）。
  raw batchは30秒粒度なので大きな問題にはならない見込み。
- 今回の調査中に、`_put_meta`が呼び出しのたびに無条件`put_object`で上書きしており、
  セッション後半の弱い再発火が強い記録（震度等）を消してしまうバグを見つけた
  （実例: `0001-59580602`の`meta.json`は`max_intensity=0.8`だが、本当のセッション
  最大は2.6）。これは本PRとは別件として切り出す。
- 今回対象範囲を確認した`#events?p=1&all=0`の12件のうち、自動確定
  （`cloud_confirmed=true`）は`0001-59580602`/`0002-59580602`の2件のみ。残り10件は
  `promote_event.py`による手動昇格（`manual=true`）で、当時ユーザーが`--pre`/`--post`
  を明示指定した別経路のため、今回の固定窓延長の対象外。この2件は既に保存済みの
  イベントなので、新しい`POST_SECONDS=600`の恩恵を受けるにはraw保持期間内
  （60日）にバックフィルが必要——別途対応する。
