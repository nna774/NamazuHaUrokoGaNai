# Shindo::currentIntensity()の静的24KBバッファを撤去し、DRAM予算を大きく回復した

## 概要

- `newBatch()`失敗対策のバッファプール化（[前回ログ](2026-08-10-newbatch-buffer-pool-handoff.md)）が
  「malloc()できる実DRAMの残り約18.5KB」という壁で見送りになった件を受け、ユーザーから
  「無駄遣いしているところはないか」と調査を頼まれた
- `nm --print-size --size-sort`でelfの静的シンボルを大きい順に見たところ、
  `gShindo`(30160B)と`Shindo::currentIntensity()::tmp`(24000B)の2つで
  静的RAM合計106100Bの過半を占めていた
- `tmp`は`currentIntensity()`が呼ばれるたび`composite_`(移動窓、6000要素)を
  丸ごとコピーして`nth_element`で30番目に大きい値を探すための作業バッファ。
  **実質的に`composite_`自体と同サイズの複製が、使う瞬間以外もずっと静的に
  確保されたままになっていた**
- `composite_`への並び替えを直接行う案（コピー自体を無くす）は、循環バッファの
  「次に上書きする位置=最古の値」という不変条件を壊すため**不可**と実測で確認した
  （後述）。代わりに「上位30個のうち最小の値」だけを最小ヒープ(30要素=120B)で
  求めるアルゴリズムに置き換え、`composite_`は読み取り専用のまま6000要素コピーを
  完全に撤去した
- 結果、静的RAM使用量が**106092B→82092B（ちょうど24000B減）**。プール化が
  見送りになった原因の「残り約18.5KB」を遥かに超える余白が戻った
- ホストg++で旧実装(`nth_element`+コピー)と新実装(最小ヒープ)を20000サンプル
  ×複数パターンで突き合わせ、全出力が一致することを確認済み。実機投入・
  `newBatch()`失敗対策（バッファプール化）の再検討はまだ

## 経緯

`docs/log/2026-08-10-newbatch-buffer-pool-handoff.md`の結合試験で、静的配置の
DRAM予算がハード的に約124.5KiBしか無く、既存firmwareが約106KBを占めていて
複数本のバッチバッファプールを積む余地が無いという壁にぶつかっていた。ユーザーから
「無駄遣いしているところはないか」という調査依頼を受け、実機ではなくホストで
`.pio/build/esp32dev/firmware.elf`をビルドし、`xtensa-esp32-elf-nm --print-size
--size-sort -C`で`.bss`/`.data`シンボルをサイズ順に洗った。

上位2つが突出していた:

```
3ffcba28 00005dc0 b Shindo::currentIntensity()::tmp   (24000B)
3ffc4204 000075d0 b gShindo                            (30160B, Shindo本体)
```

`gShindo`は震度計算に必須の状態（`composite_[6000]`=移動窓そのもの、`hist_[3][511]`=
FIRフィルタ履歴）で削れないが、`tmp`は`currentIntensity()`の中でしか使わない
一時作業領域なのに`static`で永続確保されていた。

## `composite_`を直接並び替える案は不可だった（実測で確認）

最初に試したのは「コピーを取らず`composite_`自体に`nth_element`を掛ける」案
だった。`composite_`は書き込み位置`compPos_`以外の並び順を誰も読んでいない
（`push()`は常に`compPos_`へ上書き、読むのは`currentIntensity()`のコピー元だけ）
ので、一見安全に見えた。

ところがホストで`old`実装（コピー版）と`new`実装（直接並び替え版）を突き合わせる
と、6000サンプル分の移動窓が一周した直後から震度の出力が食い違った。原因は
循環バッファのFIFO退避の不変条件が壊れること: `nth_element`は`composite_`の
要素を並び替えるが、**要素の集合自体は変えない**。しかし次回`push()`が
`composite_[compPos_]`を上書きするとき、そこにあるべき「本当に一番古い値」が
並び替えで別の位置へ移動してしまっている可能性があり、上書きが本来退避すべき
最古値ではなく別の(まだ窓内にいるべき)値を消してしまう。これを繰り返すうちに
実際の60秒移動窓の中身が正しい値集合からずれていく。

## 採用した解法: 最小ヒープでcomposite_を読み取り専用のまま走査する

本当に必要なのは「上位`kExceedSamples`(30)個のうち最小の値」だけで、6000要素
全部の並び替えは不要だった。サイズ30の最小ヒープを`currentIntensity()`の
ローカル変数（スタック上、120B）として持ち、`composite_`を先頭から走査:

- ヒープが30個未満ならそのまま積む（30個目で一括heapify）
- 30個埋まった後は、新しい値がヒープの最小値より大きければ入れ替えてsift-down

走査後の`heap[0]`（ヒープの最小値）が旧実装の`nth_element`後の`tmp[kth]`と
同じ値になる。`composite_`を一切書き換えないので循環バッファの不変条件は
壊れない。

## 検証

ホストg++でクラス名を変えた新旧2つの`Shindo`実装を用意し、同一の乱数列・
複数パターン（一様乱数20000サンプル、境界値を突く周期パターン15000サンプル。
いずれも6000サンプルの窓を複数周させて折り返しを踏む）を両方に流し込み、
`currentIntensity()`の出力を突き合わせた。全ケースで一致を確認
（`composite_`直接並び替え版は同じ突き合わせで不一致を検出できていたので、
このテスト自体が有効なことも確認済み）。

firmware側は`Shindo.cpp`の`currentIntensity()`のみ変更（`Shindo.h`のメンバは
無変更、`composite_`のサイズ・意味も変えていない）。`pio run -e esp32dev -e
adxl355 -e sensortest -e adxl355-sensortest`のビルド成功、`firmware/test/run.sh`
（wireバイト等価テスト、Shindoとは無関係だが既存の回帰確認として）を確認した。

## 次に何が可能になったか

静的RAM予算に約24KBの余白が戻った。`newBatch()`失敗対策のバッファプール化
（見送り時点で「7スロット=126448Bは失敗、6スロット=108384Bは実機のsamplingTask
起動を壊す」という状況だった）を、この余白を前提に再検討できる。ただし
結合試験で見つかった他の問題（`kMaxRamBatches=0`のUploader未定義動作、
`pump()`の原因不明の停滞）はDRAM予算とは別の話なので、それらは未解決のまま
残っている。実機（device1/device2）への投入はまだ。
