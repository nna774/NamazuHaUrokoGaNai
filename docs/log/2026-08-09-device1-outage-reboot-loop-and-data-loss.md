# 2026-08-09夜、device1が再び長時間欠測し、手動再起動しても復帰しきらなかった件を調査する

2026-08-09 19:09:46 JST頃、device1が家庭内ネット障害とは無関係に（同一WiFi上のdevice2は
生きていた）欠測した。ユーザーが物理的にボタン長押しの緊急再起動を複数回試みたが、
毎回「起動→数分〜十数分だけ送信→また無応答」を繰り返し、この調査時点でも完全復帰して
いない。[log/2026-08-08-device1-outage-and-deploy-drift.md](2026-08-08-device1-outage-and-deploy-drift.md)
（前回の70分欠測）の直接の続報。**実装は無し、調査のみ**（自己修復リブートのアイデアを
memoに残した）。

## 何が分かったか

### 1. 約2時間分のデータがS3に実在しないと確認した

`aws s3 ls` でdevice1のraw keyを直接突き合わせた（`raw/2026/08/09/<hour(UTC)>/0001-*.bin`）。

```
19:10:45 JST  最後に届いたバッチ（測定開始時刻ベース）
   ↓ raw/.../11/ （20時台JST）は0件、raw/.../10/ も19:10:45で途切れる
21:09:54 JST  次に届いたバッチ
```

**約119分、S3に一切データが無い。** ダッシュボードの`lag_s`表示だけを見て「遅れて
届く」と誤認しかけたが、S3を直接見るまで気づけなかった——[前回のログ](2026-08-08-device1-outage-and-deploy-drift.md)
で書いた「アップロード時刻だけ見るとバックフィルで埋まっているように誤認する」が
そのまま再現した。

### 2. spill容量は原因ではないと確定した

ユーザーが「spillはもっと大きくしていたはず」と指摘、確認したところ正しかった。
device1は`firmware/partitions_16mb.csv`（16MBフラッシュ、spiffs=0xBE0000 ≈ 11.87MB）を
使っており、2026-08-06のコミット`a93433a`でdevice2と同じ大容量構成に揃え済みだった。
バッチ1本18KBとして spill だけで**約676本(≒5.6時間)分**の余裕がある。2時間分
（約4.3MB相当）はこの容量に全く届かない。

**つまり`Uploader`の`dropOldestWhenFull_`（spill満杯時に最古を捨てる経路）は今回
発火していない。** 実際のボトルネックは[design.md](../design.md#送信の信頼性)に
2026-08-08時点で既に特定されていた**`gBatchQueue`（`uploaderTask`の手前、FreeRTOS
キュー、深さ4、非ブロッキング・drop-oldest）**の方だった。`uploaderTask`(Core0)が
どこかで長時間ブロックすると、`samplingTask`側は待たずに最古を1本ずつ捨てながら
積み続けるので、**`Uploader`のRAMキューにもLittleFS(spill)にも一度も到達しないまま
リアルタイムに失われ続ける**——退避漏れではなく、そもそも退避対象になっていない。
今回のシリアルログでも起動直後の`spill files on boot: 4`が実測と符合する
（spillの~676本の余裕に対して常に一桁台しか無い＝spillが埋まる前段階で失われている）。

### 3. 手動再起動は「一時的に息を吹き返すだけ」で根治しなかった

同一セッション内で3〜4回、物理ボタン長押しでの緊急再起動を行った。シリアルログ
（`.venv`のpyserialで直接ダンプ。`pio device monitor`はバックグラウンド実行だと
`termios`エラーで使えなかったため自作スクリプトで代替）を取りながら観察した結果:

- 毎回 `[boot]` → `[wifi] connecting` → `[wifi] <IP>` → `[uploader] spill files on boot: N`
  まではすぐ通る（WiFi接続自体は毎回問題なく成功する）
- その後、送信が成功する期間は数分〜十数分とまちまちだが、**必ずどこかで無応答に
  戻る。詰まった後は`[uploader] POST failed`のログすら一切出ない**——バックオフの
  上限(`kBackoffMaxMs`=60秒)を大きく超えて数分間ログが1行も出ないので、
  「失敗して再試行を繰り返している」のではなく`postBatch()`のどこか
  （TLSハンドシェイクか`http_.POST()`自体）で本当にブロックしたまま戻ってきて
  いないと判断できる
- **重要: この間、一度もtask watchdogによるパニック再起動が起きていない。**
  シリアルログで再起動理由を見ると、observedした2回とも`rst:0xc (SW_CPU_RESET)`
  ＝ボタン起因のソフトウェアリセットのみで、WDTパニックに特有のリセット理由は
  出ていない。**これは[design.md「未定事項」](../design.md#未定事項信頼性まわり2026-08-08時点)
  にある2026-08-08の「10秒のtask watchdogがTLSハンドシェイクの120秒タイムアウトより
  先に発火してパニック再起動する」という仮説と食い違う。** 今回はパニックすら
  起きず、本当にただ無限に待ち続けている
- 詰まる早さはバックログの量と相関しなかった。2時間分抱えた状態でも、
  ほぼ空(spill 4本のみ)の状態でも、どちらも同様に詰まった。**バックフィル特有の
  連続ハンドシェイクによるヒープ圧迫（design.mdの既存仮説）だけでは説明できない**
  ——空に近い状態でも起きるなら、原因はバックログの量に依存しない何かのはず
- 再起動を試すたびに、コード上`gManualRebootConfirmed`のパスで`gUploader->flushToSpill()`
  してから`ESP.restart()`するため、**RAM上のバッチ自体は毎回失わずに済んでいる**
  （前回発見した「チップ生存＋uploaderTaskだけが詰まる」パターンには手動退避が
  正しく効いている）。ただし`gBatchQueue`（Uploaderのさらに手前）は`flushToSpill()`の
  対象外なので、直近数分ぶんはボタンを押す判断が遅れるほど失われる

## 新しく浮かんだ仮説（と、それだけでは説明しきれない点）

`postBatch()`が(a)バックログの量に依らず、(b)パニックすら起こさずに無期限へ
ブロックし続ける、という2点から、batch-uplink v1.7.0で入れたTLS接続の使い回し
（`client_`/`http_`をUploaderの寿命だけ生かし`setReuse(true)`で再利用する実装、
[log/2026-08-08-uplink-v1.7.0-conn-reuse.md](2026-08-08-uplink-v1.7.0-conn-reuse.md)）が
最初に疑わしく見えた。1本送信に成功した直後に詰まるケースを複数回観測している。

ただし確認したところ、**device2も同じコードを使っている。** `firmware/platformio.ini`の
`[env:adxl355]`は`extends = env:esp32dev`で`lib_deps`（`batch-uplink@v1.8.0`固定）を
そのまま継承しており、接続使い回しは両機共通。device2は今夜も自分でPANIC再起動して
いる（別原因、未調査）が、その後は詰まらず正常に送信を続けている。**同じ再利用ロジックを
持つdevice2が今夜は再現していない以上、「使い回し自体が常に壊れる」という単純な結論には
まだ飛べない。** device1固有の何か（電波状況・再接続のタイミング・たまたま踏んだ
レースコンディション等）と組み合わさって初めて発現している可能性がある。原因はまだ
特定できていない。

## 続報: デバッグ計装を実機に入れ、意図的な全断でTASK_WDTを再現した（同日夜）

原因箇所を切り分けるため、実機にタイミング計測ログを仕込んで観察した。

### 4. `UPLINK_DEBUG_TIMING`/`LOOP_DEBUG_LOG`を追加した

`postBatch()`のどこで止まっているか（TCP接続か送受信か）を見るため、
`batch-uplink`の`Uploader::postBatch()`に`http_.begin()`/`http_.POST()`前後の
タイムスタンプ付きログを追加した（[batch-uplink#10](https://github.com/nna774/batch-uplink/pull/10)、
`-DUPLINK_DEBUG_TIMING`で既定オフ、コストゼロ）。マージ前だがコミットに直接
`v2.1.0`タグを付けて先行利用した。あわせて`firmware/platformio.ini`のpinを
`v2.0.0`→`v2.1.0`へ更新（**この過程で気づいたが、リポジトリは既にv1.8.0ではなく
v2.0.0まで上がっていた**——最初の調査で「v1.8.0のまま」と書いたのは古いキャッシュを
見ての誤りだった）。

実機で焼いて観察すると、**1本目の送信ログは完全に見えたが、2本目の
`[uplink-debug] postBatch begin`ログすら一切出ないまま無応答になった**——
`pump()`にすら到達していない可能性が浮上した。そこで`main.cpp`の
`uploaderTask`ループ本体（`connectWifi()`・`ArduinoOTA.handle()`・`pump()`の
前後）にも同じ仕組みで`LOOP_DEBUG_LOG`を追加し、どの呼び出しの前後で
最後に生きていたかを見えるようにした。

### 5. 意図的にルーターでdevice1の通信を遮断し、`TASK_WDT`を実機で確認した

「待っているだけでは自然再現を保証できない」ため、ルーター側でdevice1の
通信を意図的に遮断する実験を行った（design.mdに前から書かれていた検証方法）。

**1回目（新規接続の状態で遮断）**: `[uplink-debug] http_.POST() start`の直後、
10秒沈黙してから

```
E task_wdt: Task watchdog got triggered. The following tasks did not reset
  the watchdog in time:
E task_wdt:  - uploader (CPU 0)
abort() was called at PC 0x400eb039 on core 0
Rebooting...
[boot] reset_reason=TASK_WDT
```

が出た。これが**今夜初めて観測できた`TASK_WDT`**で、2026-08-08にdesign.mdへ
書いた「10秒のtask watchdogがTLSハンドシェイクより先に発火してパニック
再起動する」仮説をそのまま実証した。以後、**約42秒周期で自動的に
パニック→再起動→再接続→また詰まる、を繰り返した**（ボタン操作なしで
自己回復し続けている状態）。

**2回目（1本成功させ使い回し接続の状態にしてから遮断）**: 新規接続の場合と
**区別できない、同じ約42秒周期の`TASK_WDT`ループになった。** 「使い回し接続だと
違う挙動になる」という予想は外れた。

ルーターの遮断を解除すると、**どちらの場合も何も操作せず数十秒で自動的に
正常送信へ復帰した。**

### 6. ただし、これは今夜の自然発生ハングとは別物らしいと分かった

意図的な全断は`TASK_WDT`で綺麗に自己回復するのに対し、**今夜19:09〜21:09の
自然発生した断は2時間、ボタンを押すまで一度も自己回復しなかった。** もし
自然発生の断も「単純な全断」だったなら、家庭内ネットが復旧した時点で
同様に自然回復していたはずだが、実際はそうならなかった。つまり:

- 意図的な全断（今夜再現できた）→ `TASK_WDT`ループ、自己回復する
- 自然発生の断（今夜も前回も）→ パニックすら起きず、自己回復もしない、
  ボタンでしか直らない

は**別の失敗モード**である可能性が高い。「無期限に無応答・パニックも起きない」
という本命のハングパターン自体は、今回の意図的な全断では再現できなかった。
本命は全断より中途半端な接続状態（一部だけ届く・DNSだけ死ぬ等）でしか
起きないのかもしれない。原因はまだ未特定のまま。

### 7. 「時計の秒が動いていた」証言への留保

2026-08-08のログで根拠にしていた「ユーザーがTFTの時計表示を見て、単発の
フリーズだった（再起動ループではなかった）と判断した」件について、
ユーザー自身から「一度の目視で、たまたま再起動ループの"生きてる数秒間"を
見ていた可能性はないか」という指摘があった。**もっともな指摘だと判断した。**
パニック再起動はチップ全体（時計を描く`loop()`含む）を巻き込むが、起動〜NTP再同期後
数秒で時計表示は正常に戻るため、約40秒周期のループの一瞬を見ても健全に見える
（実際、今夜の意図的な全断ループの最中のログも、生きている数十秒間だけを
切り取れば完全に正常に見える）。**「単発のフリーズだった」は確定ではなく、
有力な仮説の一つに格下げする。** design.mdにも留保を追記した。

## 続報2: TASK_WDTの真因（DNS解決の内部14秒タイムアウト）を特定し、実機で修正した（同日深夜）

### 8. `setHandshakeTimeout()`実装後もパニックが1回だけ再発し、真因を特定した

`Uploader::postBatch()`用`client_`・`sendAlert()`用の一時clientの両方に
`setHandshakeTimeout(4000ms)`を設定（[batch-uplink v2.2.0](https://github.com/nna774/batch-uplink/pull/11)）。
実機で試すと大半の失敗はHTTPClient既定の接続タイムアウト(5000ms)で綺麗に
`code=-1`を返すようになったが、**6回に1回程度、依然として10秒ブロック→
`TASK_WDT`が再発した**（`ssl_client.cpp`の「5秒で諦めた」ログが出ないまま無応答）。

`WiFiClientSecure::connect()`のソースを読むと、`start_ssl_client()`（接続タイムアウトと
ハンドシェイクタイムアウトが効く範囲）より**手前**で`WiFi.hostByName()`
（`WiFiGeneric.cpp`）を呼んでいた。この内部実装:

```cpp
waitStatusBits(WIFI_DNS_DONE_BIT, 15000);  //real internal timeout in lwip library is 14[s]
```

**DNS解決だけで最大15秒（lwIP内部は14秒）ブロックしうる**——ここはHTTPClientの
接続タイムアウトにもUploaderのハンドシェイクタイムアウトにも一切守られていない
別枠だった。DNSキャッシュが効いている間は素通りするので気づかず、キャッシュが
切れて再解決が必要になった瞬間だけ発現する。これが「5秒で失敗する時」と
「10秒で死ぬ時」が同じ遮断状態で両方観測された理由。

対策は、DNSという制御できない待ちを見越して**task watchdog自体を10秒→20秒へ
拡張**（`main.cpp`）。実機で再試験したところ:

```
http_.POST() start ... t=344214635
（ちょうど14.04秒後）
hostByName(): DNS Failed for 5uglpx52w...lambda-url...
http_.POST() -> code=-1
[uploader] POST failed code=-1
```

**lwIPの内部タイムアウト「14秒」とぴったり一致し、パニックせずに正常復帰した。**
20秒WDTでDNS最悪ケースを飲み込めることを直接実証した。

batch-uplink側は`v2.2.0`（ハンドシェイクタイムアウト）をコミット後に一旦
revertして[PR #11](https://github.com/nna774/batch-uplink/pull/11)を正式に作り直した
（最初直接masterへコミットしてしまい、「PRにしておいて」と指摘されたため）。

### 9. `gBatchQueue`吸い出しは今回の対策だけで正常に機能すると確認できた

修正後、全断状態のまま`enqueue()`にもログを足して（batch-uplink v2.3.0）
観察したところ、`batch complete #N`→`enqueue #N`が1:1で対応し`ram`が
0→1→2→3と正しく伸び続けた。**`gBatchQueue full`のドロップも一度も出ず**、
送信が失敗し続けてもUploaderの吸い出し自体は正常に継続することを確認した。
design.mdで合意済みの「吸い出し/送信の2タスク分離」は、今回確認できた
失敗モードに対しては必須ではなくなった（ただし未知の無限ブロックへの保険
としての価値は残る、と結論）。

### 10. 新しい謎: `newBatch()`がヒープに余裕があるのに失敗し、バッチ形成自体が止まる

さらに長時間（数分）観察を続けると、**特定のバッチ以降、新規バッチが
一切完成しなくなる**現象を発見した。`heap_free`が78400付近で完全に静止し、
`batch complete`のログが数分間途絶える。`samplingTask`側の3経路
（`gSensor.read()`失敗・`timesync::isSynced()`偽・`newBatch()`失敗）に
エッジ検知ログを追加して原因を特定:

```
batch complete #5 t=154066921
newBatch invalid, retrying next sample heap_free=78520 maxblock=45044 t=154078161
```

**`newBatch()`が失敗している。** ただし`maxblock=45044`はバッチ1本(18038バイト)の
倍以上あり、単純な空き容量不足には見えない。`ESP.getMaxAllocHeap()`が報告する
「確保可能な最大ブロック」と`namzwire::newBatch()`が実際に要求しているメモリの
種別（capability、例えばDMA対応領域限定等）が食い違っている可能性が高い——
一般ヒープには余裕があるように見えても、特定の種類のメモリだけ枯渇している
のかもしれない。**未解明、調査継続中。**

### 11. `newBatch()`失敗の正体を実測で特定: `MALLOC_CAP_INTERNAL`と`MALLOC_CAP_8BIT`の乖離

`config.h`に既に前例があった。ADXL355機のバッチ長を半分にした理由として
「mbedTLSのハンドシェイクがBIGNUM確保に失敗した（実機で`BIGNUM - Memory
allocation failed`）」というコメントが残っている。TLSハンドシェイクは
大きな一時バッファを確保・解放するので、接続失敗を繰り返す＝まさに障害中に
ヒープが断片化する、という前例と同じ筋がここでも疑わしい。

`ESP.getMaxAllocHeap()`は内部で`heap_caps_get_largest_free_block(MALLOC_CAP_INTERNAL)`
を呼んでいる（`Esp.cpp`で確認済み）。一方`Batch`のバッファは素の`malloc()`——
実際に要求しているcapabilityは`MALLOC_CAP_8BIT`のはず。ESP32の内蔵RAMは
8bitアクセス可能なDRAM/D-IRAMと、32bit単位でしかアクセスできないIRAM専用
領域が混在するため、**`INTERNAL`基準の最大空きブロックは、`malloc()`が実際に
使える`8BIT`基準の最大空きブロックより大きく見えることがありうる**、という
仮説を立てた。

検証のため`main.cpp`の`newBatch invalid`ログに
`heap_caps_get_largest_free_block(MALLOC_CAP_8BIT)`を並べて出すよう
計装を追加（`#include <esp_heap_caps.h>`）し、再ビルド・再フラッシュして
同じ手順（正常運転を数サイクル確認→ルーターで全断）で再試験した。

```
[loop-debug] newBatch invalid, retrying next sample heap_free=78240 maxblock_internal=45044 maxblock_8bit=17396 t=523314067
```

**確定した。** `maxblock_internal`(45044)は必要な18038バイトの倍以上あるのに、
`maxblock_8bit`(17396)は**18038に対して642バイトだけ足りない**。
`ESP.getMaxAllocHeap()`は`malloc()`が実際に使える量を2.6倍近く過大報告して
おり、これが「ヒープに余裕があるように見えるのに`newBatch()`が失敗する」の
直接の原因だった。断片化そのものの発生源（mbedTLSの一時確保か、他の要因か）
は未特定だが、**症状の正体は理論ではなく実測で切り分けられた。**

なお同じ再試験の前半で、ネットワークを切ったまま起動した場合に
`samplingTask`側のログが一切出ない（バッチが全く作られない）という
別の混乱があった。これはバグではなく、`timesync::isSynced()`(=SNTP同期)が
ネット無しでは完了せず、`samplingTask`が同期待ちで`continue`し続けるだけ
という想定通りの挙動だった（`TimeSync.cpp`は`esp_sntp`そのもの）。
ネットを戻すとSNTPが同期し、バッチ形成が正常に再開することを確認した。

対策の方向性として、`Batch`のバッファを毎回`malloc`/`delete`するのではなく
固定サイズのバッファを静的に確保して使い回す案を検討した。`Uploader`は
バッチの所有権を受け取り自身で`delete`する契約（`enqueue()`のコメントに
明記）なので、素朴に「使い回す」だけだと解放タイミングで衝突する。
`Batch`に外部バッファ用コンストラクタと解放コールバック(`onRelease`)を
追加し、**ラッパーオブジェクト自体の`new`/`delete`はUploader側そのまま
（所有権の契約は変えない）にしつつ、内部の生バッファだけプールへ返す**
設計まで固めたが、**実装はまだ行っていない**（batch-uplinkに新ブランチ
`external-buffer-batch`を作っただけで、コミットはゼロ）。次にやるなら
そこから。

## 次に考えないといけないこと

- **`newBatch()`失敗の直接原因(`MALLOC_CAP_INTERNAL`と`8BIT`の乖離)は特定できた。**
  次は対策の実装——`Batch`に外部バッファ+解放コールバックを追加し、
  `samplingTask`側に固定バッファプールを持たせる案を設計済み（batch-uplink
  `external-buffer-batch`ブランチ、コミットはまだ無し）。RAM予算（プールの
  スロット数）の検討も未了
- 本命の「無期限無応答・パニック無し」ハングは意図的な全断では再現できなかった
  （全断は`TASK_WDT`で自己回復するとわかった）。次に自然発生した時に備え、
  デバッグ計装は既定有効のまま残す
- design.mdの「吸い出し/送信2タスク分離」は今回の失敗モードには不要と分かったが、
  未知の無限ブロックへの保険としては引き続き実施する価値がある。ユーザーからは
  「別セッションで着手するかも」との意向あり
- batch-uplink [PR #10](https://github.com/nna774/batch-uplink/pull/10)（v2.1.0）・
  [PR #11](https://github.com/nna774/batch-uplink/pull/11)（v2.2.0、handshake timeout）は
  タグは切って実機検証済みだがマージはまだ。マージ判断は保留中
- device1固有の環境要因（WiFi RSSI、AP側のログ、device2との配置差）を次に
  実機で見に行く時に比較する

## 次に何が可能になったか

「spillを大きくしたのに2時間分消えた」という一見矛盾する状況を、実際には
spillの手前(`gBatchQueue`)で失われていたと確認できたことで、容量を増やす方向の
対策が無意味だと分かった。**TASK_WDTパニックの真因（DNS解決の内部14秒
タイムアウト）を特定し、WDTを20秒へ拡張・ハンドシェイクタイムアウトを4秒に
短縮する対策を実機で実証まで完了した**——意図的な全断でパニックせず正常復帰
することを確認できた。`gBatchQueue`starvationもこの対策だけで解消すると確認でき、
2タスク分離は緊急度が下がった。一方で`newBatch()`がヒープに余裕があるのに
失敗するという新しい謎が見つかり、次の調査対象が明確になった。「単発フリーズ
だった」という前回の結論も一次証言のみに基づく弱い
根拠だったと明確になり、design.mdの記述を訂正した。
