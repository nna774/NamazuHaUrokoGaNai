# バッチ完了直後にLittleFSへ退避する「常時spill化」を実験実装（未採用）

前回のRTC memory検討（[log/2026-08-30-esp32-hidden-features-survey.md](2026-08-30-esp32-hidden-features-survey.md)）
で候補に挙げた「組み立て完了時点で送信前に必ずLittleFSへ書く」を実装した。
ユーザー指示「採用するかどうかまだ考え中だけど、一旦コードにしてみて」により、
**別PRとして実装のみ済ませ、マージ判断は保留**。

## docs/design.mdとの矛盾を先に確認した

実装前に`docs/design.md`「送信の信頼性」の検討済み案一覧に、この「常時spill化」が
**既に一度保留と記録されている**のを見つけた:

> 常時spill化: flash摩耗は問題にならないと試算済みだが、健全時のI/O負荷が乗る上に
> タイムアウト無制限という根本原因を直さない対症療法になるため保留（根本対策=上記の
> タイムアウト予算を先に実施）

これは2026-08-07のdevice1 70分ブロッキング障害（`uploaderTask`が単一のブロッキング
呼び出しで70分詰まり、その間退避が1本も走らなかった）への対症療法として検討された
もので、根本原因（タイムアウト無制限）は既に別対策（`postBatch()`の3区間タイムアウト
予算、最悪合計12秒）で解消済み。

今回の動機は別——**WDTパニック等の瞬時再起動で、送信直前にRAM上にしか無いバッチが
消える窓**を塞ぎたい、というもの。これはタイムアウト予算では塞げない（パニックは
一瞬なので）。ただし「健全時に常時LittleFS I/O負荷が乗る」というコスト自体は
過去の判断理由と変わらず残る。ユーザーに確認した上で、今回は別目的での実験実装として
進める判断になった。

## 実装

`batch-uplink`の`Uploader::flushToSpill()`（RAMキューを丸ごとLittleFSへ退避、OTA・
リモート再起動前に既に使用中のAPI）が既にあったため、batch-uplink側の変更は不要
だった。呼び出し側で「バッチを`enqueue()`した直後に`flushToSpill()`も呼ぶ」だけで済む。

- `main.cpp`の`batchDrainTask`（吸い出し専用タスク、ネットワークI/Oを持たない）:
  `gUploader->enqueue(b)`の直後に`gUploader->flushToSpill()`を追加
- `piezo_main.cpp`の`uploaderTask`（吸い出しと送信が同一タスク）: `gBatchQueue`から
  ドレインするwhileループの直後、`pump()`より前に`flushToSpill()`を追加（drainした
  ものが無ければ呼ばない）

`flushToSpill()`はファイルI/Oのみでネットワークを触らないため、`batchDrainTask`を
送信タスクと分離した本来の目的（送信側のブロックに巻き込まれない）は損なわれない。

## 確認したこと

- firmwareビルド: `esp32dev`・`adxl355`・`piezo`の3env
- `firmware/test/run.sh`（wire形式golden、ヘッダ配列と無関係の変更なので当然だが確認）
- **実機での動作確認・flash摩耗の実測・健全時I/O負荷の実測はまだ**
