# クラウドセッションでの事後解析の前提を手順書に書いた

同日、クラウドセッションで9件の事後解析
（[上越M2.4](2026-11-27-joetsu-m2.4-post-hoc-detection.md)・[11-21〜11-27の8件](2026-11-27-post-hoc-detection-1121-1127.md)）を
解析から昇格・relateまで通した。そのとき確認した環境の前提と、そこで使った見方を
[docs/post_hoc_detection.md](../post_hoc_detection.md)に書いた。

## 決めたこと

- **クラウドセッションの前提を手順書の節にした**（`namazu-analysis`ロールの権限、`.venv/bin/aws`、
  `terraform`が無いこと、許可されている通信先、和文フォント）。次のセッションが同じ確認をやり直さずに済むよう、
  CLAUDE.mdの「ローカル環境」節からリンクした。
- **「近距離の小地震では2-20Hzで両機のonset一致を見る」を手順書に入れた。** 上越M2.4のログでは
  「1例なので手順書にはまだ載せない」としていた。同じ日に会津M3.8（80km）でも0.11秒差の一致が出て2例になったので、
  経験則として載せた。合わない例が出たら直す前提で、その旨も手順書に書いた。
  device1の誤検出が多いことも併記した（上越M2.4のログにある「前3分に候補なし」は偶然だった）。
- **P/Sの読みが曖昧な時の「2仮説で機間相関の山の絶対時刻を比べる」を手順書に入れた**（能登M3.8で使った）。

## 確認したこと（変更なし）

- **会津M3.8（標準設定で両機STA/LTA閾値超過）でデバイス速報が立たなかったのは設計どおり。**
  ファームの速報は`kAlertIntensity=0.5`・`kAlertHoldSeconds=2.0`（リアルタイム震度0.5以上が2秒）、
  クラウドのdetectも`NAMZ_DETECT_THRESHOLD=0.5`で、どちらも震度基準である。会津M3.8の計測震度は
  -0.1/-0.5で、条件に届かない。detectlabのSTA/LTAは背景との相対値なので、震度0に届かない揺れでも閾値を超える。
  「震度0.5未満でもSTA/LTAで拾う」経路は今のところ持たない設計で、それを変える判断はしていない。
- 環境変数`AWS_SECRET_ACCESS_KEY`は、クラウド環境の設定に名前だけ登録されている。セッションのプロセスには渡っておらず、
  何にも効いていない。

## 未対応

- `namazu-analysis`ロールに`namazu-devices`の読み取りを足す件。ロールは別リポジトリで管理しているので、そちらで扱う。
