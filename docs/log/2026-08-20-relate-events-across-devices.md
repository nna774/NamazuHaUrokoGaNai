# 複数デバイスのイベントを「同じ地震」として相互リンクする

## 何を決めたか

地震が起きたとき「検知した機体だけでなく全デバイスの波形をイベントとして保存したい」
という要望から検討を始めたが、**自動で他機の波形を確保する仕組み（detect確定時に他機の
raw も events/ へコピーする案）は保留し、まず手動リンクだけ実装した**。

- `tools/flag_event.py` に `relate`/`unrelate` サブコマンドを追加。複数の event_id
  （device_id ごとの別レコードのまま）を `related_events` フィールド（相互・対称の
  event_id リスト）で束ねる/外す。
- `lambda/api/handler.py` の `_event()` が `related_events` をそのまま返す。
- `dashboard/app.js` のイベント詳細に「関連イベント（同一地震・他機）」の行を追加し、
  リンクをクリックすると他機のイベント詳細へ遷移する（既存の `event/<id>` ルーティングを
  そのまま使う。新しいAPIエンドポイントは無い）。

## なぜそう決めたか

- 検討の出発点は「地震が起きたら結局全デバイスの波形を残しておきたい」だったが、
  そのためには **detect の確定タイミングで他デバイスの同時刻 raw がもうS3に届いて
  いるか**を確認する必要があった。通常運用（120秒窓+最大30秒strideのラグ、各機とも
  バッチ送信は成功時ノーウェイトで即再送）なら大体揃うが、device1 の70分欠測
  （バックフィル無しで消失した実績、[2026-08-08のログ](2026-08-08-device1-outage-and-deploy-drift.md)）や
  device3 のRAMキューの浅さ（`kMaxRamBatches=1`）を踏まえると、確定時の同期コピー
  一発では取りこぼす。確実にやるなら「confirm時の即時コピー＋後追いの定期リトライ」の
  2段構成が要る、という設計まで詰めたところで、**運用の実態が変わった**：
  現状はデバイス3台の据え付けがまだ流動的で、当面は自動検知より
  `promote_event.py` 等での手動イベント化が多くなりそう、という判断が出た。
- 自動で全機コピーする仕組みは「今すぐ要るもの」ではなく「そのうち要るかもしれないもの」
  になったため、**先に安く作れて今すぐ使えるもの**（既存イベント同士を後からリンクする
  だけの機能）を優先した。手動でイベント化した各機のレコードを見比べたい時、
  リンクを張ればダッシュボードから行き来できる。

## 何が覆ったか

前回の会話で「confirm時の即時コピー＋定期リトライ」の2段構成で進める方向にいったん
合意していたが、これは実装せず据え置いた。

## 次に何が可能になったか

- 地震（や較正用のタップ試験）で複数機がイベントを持った時、`flag_event.py relate` で
  手動リンクしてダッシュボードから行き来できる。
- 自動全機コピーが必要になったら、`related_events` のデータモデル（対称リンクの
  event_id リスト）はそのまま自動書き込みにも転用できる——detect側で companion event
  を作る時に同じフィールドへ書けばよく、ダッシュボード側の表示コードは変更不要。
