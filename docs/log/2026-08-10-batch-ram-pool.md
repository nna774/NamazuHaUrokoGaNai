## 重要な前提: 同じ実験を別の並行セッションが今日すでに試し、ロールバックしていた

実装に入る前に`docs/log/2026-08-10-newbatch-buffer-pool-handoff.md`を確認したところ、
**別の並行セッション（同じ日、別worktree）がほぼ同じ実験を既に実機で試し、一旦
見送っていた**ことが分かった。要点:

- `batch-uplink`の外部バッファ+解放コールバック版`Batch`コンストラクタ
  ([PR #13](https://github.com/nna774/batch-uplink/pull/13))は**既にマージ済み**
  （v2.4.0で導入、現行pin v2.8.0にも含まれる）。新規タグは不要、既にAPIが使える。
- そのセッションはプールを「組み立て中1本+`gBatchQueue`深さ4+`kMaxRamBatches`」の
  合計スロット数（当時7本=126448B）で確保しようとし、**実機でsamplingTaskの
  生成に失敗しパニック再起動をループした**。isolatedな`pool_probe_main.cpp`での
  検証はDisplay/TFT_eSPIのフォント読み込み等、本番firmwareが食う分を見落として
  おり、実機の余裕は見た目より少なかった。
- 5スロットまで削っても、今度は「`pump()`が`spillCount_=4`を抱えたまま60秒間
  一度も送信を試みない」という別の謎の停滞を踏んだ（プールを迂回しても再現）。
- 直すたびに別の症状が出る状態が続いたため、**`main.cpp`/`config.h`を
  プール導入前の状態へ完全に戻し、一旦見送った**（`928bd9c`、既に`origin/master`
  にマージ済み）。

この「pump()が60秒間送信を試みない」という症状は、**このセッションが実機ログで
確定させた`malloc(18032)`/`MALLOC_CAP_8BIT`断片化ちょうど17396バイトでの詰まりと
同一現象である可能性が高い**——プールを迂回した(=素のmalloc版に戻した)後も再現した
という記述と、フォールバック時は結局同じ一般ヒープのmalloc(18032)を叩くという
構造が一致する。両セッションの観測は矛盾しておらず、同じ根の別の見え方だったと
考えられる。

また、そのロールバック時点(`928bd9c`)は**PR #59/#60/#61（合計約28KBの静的RAM
削減）より前**だった。今回はその28KB増加分がある状態から再挑戦する。

## 今回の実装方針: 前回よりスロット数を大幅に絞る

前回の「組み立て中1+`gBatchQueue`深さ4+`kMaxRamBatches`」という見積もりが
実機のクラッシュを招いた反省を踏まえ、**今回は`kMaxRamBatches + 1`（現状3本、
54192B）だけを確保する**保守的な設計にした。`gBatchQueue`(深さ4)側の滞留分は
数えず、プールが尽きたら素朴なmalloc版へフォールバックする安全策に任せる
（`gBatchQueue`の滞留時間は`pump()`が毎ループ即座に吸い出そうとするため通常
非常に短く、静的に確保してまで守る優先度は低いと判断した）。

実装（`firmware/src/main.cpp`）:

- `kBatchBufferBytes`(=18064B、`kWireHeaderSize+kBatchSamples*recordBytes+
  kMaxTrailerBytes`)を算出し、`kBatchPoolSlots`(=`kMaxRamBatches+1`)ぶん
  `setup()`冒頭（TlsMemPool設置直後、Display/SPI/センサ初期化より前——理由は
  前回の反省と同じ「本番firmwareが食う分を過小評価しない」ため）で`malloc()`
  一発確保する。
- `newPooledBatch()`が`gBufferPool`(空きバッファ用`QueueHandle_t`)から借りて
  `Batch`の外部バッファ版コンストラクタを使う。プール枯渇時・`malloc()`自体が
  失敗した時はどちらも`namzwire::newBatch()`(従来のmalloc版)へ自動フォール
  バックする(クラッシュしない、pooling効果が無くなるだけ)。
- 副産物として見つけた実バグを直した: `xTaskCreatePinnedToCore()`の戻り値が
  `samplingTask`/`uploaderTask`ともに未チェックだった。前回の並行セッションが
  踏んだクラッシュ（`gSamplingTask`が不定値のまま`vTaskNotifyGiveFromISR`が
  呼ばれ分かりにくいアサートで落ちる）は、今回は同じ状況でも「戻り値を見て
  分かりやすいメッセージを出して停止する」形になる。

`pump()`のspill読み込み用バッファ(`Uploader.cpp`内`malloc(len)`)の固定バッファ化
（議論での案2）は**今回は見送った**。1回の`pump()`内で確保・解放が完結する
一時確保であり、居座る側（Batch本体）ほど断片化への寄与が強いという確信が
持てなかったのと、`batch-uplink`側の変更（新タグ切り直し）が要るぶん着手
コストが高いため。Batchプールの効果を先に実機で見てから、必要なら着手する。

## 実機検証

`env:fake-sensor`でビルド・実機(予備基板、`/dev/cu.usbserial-5B320272871`)へ
書き込み。`pio run -e esp32dev -e fake-sensor -e adxl355`のビルドはいずれも
成功（3センサ設定とも`kBatchRecordBytes`の分岐が正しくコンパイルされることを
確認）。

起動ログ:

```
[boot] NamazuHaUrokoGaNai fw=40d87cc-dirty env=esp32dev
[tls-pool] installed: 53248 byte dedicated pool for mbedTLS
[pool] batch buffer pool: 3 slots x 18064 B = 54192 B free_heap=159324 maxblock_8bit=57332
[boot] reset_reason=POWERON
[sensor] FAKE ready
[wifi] connecting.
[wifi] 10.255.255.159
[uploader] spill files on boot: 0
[mem] free heap 89772 maxblock 45044, batch 18000 B x 2
```

- Batchバッファプールのmalloc()は成功。TlsMemPool(53248B)確保後でも
  free_heap=159324、maxblock_8bit=57332という大きな余裕が残っている——前回の
  並行セッションが7スロット(126448B)で失敗した時点より明らかに健全。
- `samplingTask`/`uploaderTask`とも生成失敗ログ(`[boot] BUG: ...`)は出ていない。
  前回セッションが踏んだパニック再起動ループは再現していない。
- 通常運転(30秒ごとにバッチ形成→即送信)を2サイクル観測、両方
  `postBatch(ram) -> 1`(=送信成功)。heap_free/maxblockはサイクル間で
  ほぼ変化なし(79240→79024、maxblock=45044のまま)——プール導入前のセッションで
  見えていた「サイクルを追うごとにmaxblockがじわじわ減る」傾向が、少なくとも
  この短時間の観測では見えていない。
- `[pool] buffer pool exhausted`（プール枯渇によるフォールバック発生）ログは
  出ていない。通常運転下ではBatch本体の確保が常にプール経由になっている
  ことを意味する——設計上、平常時は一般ヒープのmalloc(18032)を一度も
  叩かなくなったはず。

## 未検証: 断片化ストレス下(バックログ滞留)での再検証

このセッションが実機で確定させた「51→9(42件)まで進んでstall」という条件
（`kMaxRamBatches=2`のみ、Batchプール無し）と同じストレス（spill詰まりを
作った状態からの復旧）でBatchプール込みを再現すれば、直接的な効果測定に
なる。ただしそのストレスはWiFi断（実際の断、または人為的な切断）が要り、
このセッションからは物理操作ができないため未実施。現時点で確認できたのは
「クラッシュしない」「平常運転でプールが機能している」ところまで。

## 次に何が可能になったか

- Batchバッファの固定プール化が、前回の並行セッションが実機で踏んだクラッシュを
  再現せずに動くことを確認できた（スロット数を絞ったこと・初期化順序・
  タスク生成の戻り値チェックの3点が効いたとみられる）。
- 平常運転下では、設計上Batch本体がもう一般ヒープのmalloc(18032)を叩かない
  状態になった。長時間運転での断片化耐性が上がっている見込みが強い。
- 残る検証（断片化ストレス下での比較）と、`pump()`のspill読み込みバッファの
  固定化（見送った案2）は次の一手として残る。自己修復リブート
  （`firmware_selfheal_reboot_idea.md`）はこの対策と独立に依然有効な保険。
