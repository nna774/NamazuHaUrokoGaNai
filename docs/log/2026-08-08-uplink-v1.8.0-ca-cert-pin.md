# batch-uplinkのTLS証明書ピン留めを実装し、v1.8.0へ追従する

[前回のログ](2026-08-08-uplink-v1.7.0-conn-reuse.md)末尾で「証明書ピン留め(TODO)は
別セッションに切り出そうとして失敗した」と書いた残課題。GitHubの連携状況に関わらず
このセッションでそのまま着手できたので、`Uploader`側にping留め用のAPIを足し、
Namazu側の呼び出しを実際に証明書検証ありへ切り替えた。

## 何をしたか

- `batch-uplink`側: `Uploader`コンストラクタ末尾に`const char* caCert = nullptr`を
  追加（[batch-uplink#8](https://github.com/nna774/batch-uplink/pull/8)、マージ済み）。
  渡すとingest用`client_`・alert用の一時`WiFiClientSecure`の両方で`setCACert(caCert)`
  を使う。渡さない場合は従来通り`setInsecure()`にフォールバックするので、Electabuzz側は
  無改修で動く。証明書の実体（PEMそのもの）はライブラリに埋め込まず、呼び出し側に
  委ねる設計にした——ingest/alert先のドメイン・証明機関はプロジェクトごとに違いうるため
- `v1.8.0`タグを切ってpush
- Namazu側: `firmware/platformio.ini`の`lib_deps`と`terraform/build_lambda.sh`の
  `UPLINK_VERSION`を両方`v1.8.0`へ更新
- `firmware/src/main.cpp`の`new Uploader(...)`呼び出しに、OTA用に既に埋め込み済みの
  `amazon_root_ca1_pem_start`（`certs/amazon_root_ca1.pem`、`board_build.embed_txtfiles`
  でリンク）をそのまま`caCert`として渡すよう変更。新しいPEMを追加で埋め込む必要はなかった

## 確認したこと

- ingest先（`https://5uglpx52w3n7ktm3clomjt5rfa0nmocn.lambda-url.ap-northeast-1.on.aws/`、
  Lambda Function URL直・CloudFrontを介さない）へ`openssl s_client -showcerts`で実際に
  接続し、証明書チェーンが `leaf(*.lambda-url.ap-northeast-1.on.aws)` →
  `Amazon RSA 2048 M01` → `Amazon Root CA 1` であることを確認した。OTA用ドメイン
  （`namazu.dark-kuins.net`、CloudFront経由）とは配信経路もドメインも別だが、どちらも
  AWS/ACM発行で同じ`Amazon Root CA 1`に辿り着くため、OTA用に埋め込み済みの1本で
  ingest/alert双方を検証できる
- `firmware/`のesp32dev・adxl355両envで、実際に`https://github.com/nna774/batch-uplink.git#v1.8.0`
  を取得してのビルド成功を確認
- `PYTHON=.venv/bin/python terraform/build_lambda.sh`（`UPLINK_VERSION=v1.8.0`）成功
- `pytest lambda/tests tools/tests`（149件）・`firmware/test/run.sh`（wire形式のバイト
  等価テスト）通過

## 次に何が可能になったか

`docs/design.md`「送信の信頼性」節の未定事項だった証明書ピン留めが実装済みになった。
まだ実機へは配信していない（pull型OTAでの配信、または再flashが必要）。今回はコードと
ビルド確認までで、`terraform apply`によるLambda更新・実機への配信は別途行うこと
（このログの時点では未実施）。
