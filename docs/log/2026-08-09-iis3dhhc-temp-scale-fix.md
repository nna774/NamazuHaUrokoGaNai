# IIS3DHHC温度換算式の桁ズレを実機投入直後に発見・訂正した

## 何を決めたか

[iis3dhhc-embedded-temperature](2026-08-09-iis3dhhc-embedded-temperature.md)で実装した
`lambda/common/wire.py`の`iis3dhhc_temp_c()`が`raw/16+25`だったのを`raw/256+25`に直した。

## なぜ

実機（1号機）へOTA配信して初めて温度データを取ったところ、raw=2816 が
`raw/16+25`では201℃になり物理的にありえなかった。

STの公式ドライバ`iis3dhhc-pid`の`iis3dhhc_from_lsb_to_celsius()`は`lsb/16+25`だったので
そのまま使ったが、これは**12bit値を渡す前提の関数**であり、レジスタから読んだ
16bit生値をそのまま渡すものではなかった。公式データシート(DS12292 §7.6)を読むと
`OUT_TEMP_L`/`OUT_TEMP_H`の16bitは実体が12bit値の**左詰め**（`OUT_TEMP_L`の下位4bitは
常にパディング0）。実測raw値（2816=0x0B00, 2752=0x0AC0, 2784=0x0AE0）も下位4bitが
すべて0で、この左詰め仕様と一致した。

12bit値への変換は16bit生値を4bit右シフトするのと同じなので、`/16`の代わりに
`/256`を使えば同じ結果になる（下位4bitが必ず0である以上、桁落ちなく厳密に等しい）。

## 何が覆ったか

前回の実装ログで「STの公式ドライバのソースを直接確認したから正しい」と判断したが、
**ドライバのソースだけでは関数の入力契約（12bit値前提）まではわからなかった**。
データシートのレジスタ記述（左詰め・パディング）を読むまで気づけなかった。

## 次に何が可能になったか

`lambda/common/wire.py`の`temp_c_for`が返す℃が実際の値になった。Lambda再デプロイのみで
直る（`namazu-device-temp`にはrawだけ保存し℃は読み出し時に計算するため、ファーム再書き込み・
過去データのバックフィルは不要）。

pytest 109件通過。ファーム側は無変更（送っているビット列自体は元から正しかった）。
Lambda再デプロイと実機での再確認はこのコミットの後に行う。
