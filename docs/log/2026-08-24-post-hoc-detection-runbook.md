# 2026-08-24 事後解析の手順書(docs/post_hoc_detection.md)を新設した

「〇〇地震、うちの震度計は捉えてた？」と聞かれるたびに同じ手順（起点の震源要素確認→
`/events`で自動検知の有無確認→detectlabで標準設定・必要なら低帯域設定を試す→ログを書く→
無ければ`promote_event.py`で手動イベント化）を毎回その場で組み立てていた。
[浦河沖M6.0の事後解析](2026-08-24-urakawa-oki-m6.0-post-hoc-detection.md)を終えた直後に
ユーザーから「手順書があると洗練させていけて便利」との要望を受け、実際にやった手順を
一般化して`docs/post_hoc_detection.md`として切り出した。

## 決めたこと

- **起点は2種類**: tenki.jpの地震詳細ページURL、または気象庁電文形式のテキスト
  （例:「2026/08/23 22:45:06 第1報 (2026/08/23 22:44:55発生)震央:N41.8/E143.0(浦河沖)
  深さ30km 最大:M6.1 震度4」のような文字列）をユーザーがそのまま貼ることがある。
- **拡大（2分窓ズーム）図は既定では作らない。** 標準設定・低帯域設定の8-10分窓図だけで
  説明がつくならそれで十分——今回の浦河沖M6.0では2分窓ズームも作ったが、ユーザーから
  「拡大版は普通は別にいらない。必要ならつくってもらう」という指摘を受けたため、
  手順書では「人間から頼まれた時だけ追加で作る」補助手順に格下げした。
- **CloudFront invalidationの要否は「既存event_idの書き換え時だけ」**という基準
  （[#141](https://github.com/nna774/NamazuHaUrokoGaNai/pull/141)で確定）をそのまま
  手順書の手動イベント化の節に埋め込んだ。
- `docs/noise.md`「検出できた／できなかった」節の判定基準（probable detection / 微妙 /
  完全埋没）を手順書からも参照できるようにし、判定の言葉遣いを過去ログと揃えた。

`CLAUDE.md`「ドキュメントの歩き方」表にもエントリを追加した。今後この手順で迷った点や
新しい知見が出たら、ログを書くだけでなく`docs/post_hoc_detection.md`自体を更新して
洗練させていく。
