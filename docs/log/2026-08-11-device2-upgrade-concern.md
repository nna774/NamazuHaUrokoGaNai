# 2号機は今回の修正一式を持っていない。焼き直す前の懸念点を記録する

## 背景

`docs/log/2026-08-11-batch-pool-fallback-heap-corruption.md`の一連の修正
（fix #1: Batchプール枯渇フォールバック撤去、fix #2: `pump()`のRAM優先化、
`batch-uplink` v2.11.0）はdevice1(1号機)の実機で検証した。2号機(ADXL355)は
最近焼いておらず、稼働中のfirmware版数は`ba23fb3`（2026-08-09 01:36、WDT
panic説の調査ログを書いた時点のコミット）のまま——**TlsMemPool・Batch
バッファプール・spill読み込み固定バッファ・今回のfix #1/#2、いずれもこれ
より後に入った変更で、2号機は一つも受け取っていない**。

## なぜ2号機は今まで大丈夫だったか（当時の仮説の再確認）

2号機の実運用での体感は「インターネット断のあと、1号機はいつも帰ってこれず、
2号機は毎回復帰できている」（`docs/log/2026-08-10-tls-dedicated-pool.md`
続報2）。`ba23fb3`時点の`config.h`を確認したところ:

```
kMaxRamBatches: ADXL355(2号機)=3 / それ以外(1号機)=6
```

当時1号機だけ`6`だった（`2026-08-10`に実験的に`2`へ縮小されたのは
この後）。バッチ本体は両機とも同じ約18KBなので、RAMキューの最大占有量は
1号機108KB・2号機54KBとちょうど倍の差があった。**2号機が強かったのは
今回判明した諸々の対策のどれでもなく、単純にRAMキューへ抱え込む量が
元から少なかったから**、という当時の仮説がそのまま生きている。

## 今回の修正込みで2号機に焼いた場合の懸念

現行`config.h`は`kBatchSeconds`が2号機15秒・1号機30秒、`kMaxRamBatches`は
2号機3・1号機2（`kBatchPoolSlots`は2号機4・1号機3）。

Batchプール枯渇レース（`ram_`が上限＋`gBatchQueue`待機1本＋組み立て中1本＝
上限+2本要るのにプールは上限+1本しかない、という構造的な1本不足）は
`kMaxRamBatches`の値によらず常に存在する。一方、DNS解決の詰まりは
14〜20秒ブロックする(`WiFi.hostByName()`内部タイムアウト14秒/WiFi再接続
20秒)。2号機のバッチ周期(15秒)はこのブロック時間と同程度以下——1回の
詰まりが終わる前に次のバッチができてしまう確率が、周期30秒の1号機より
高い。

**つまり今回の修正一式を2号機にそのまま焼くと、fix #1が安全に処理する
`[sampling] newBatch stuck`（一時的な生サンプル欠測）自体は、1号機より
高頻度に出る可能性がある。** ただしfix #1により「安全な欠測」止まりで、
旧コードのようにヒープを破壊して復帰不能になる話には繋がらないはず——
これは実測していない推測で、確信は無い。

## 決定事項

**2号機への投入はまだ行わない。** テスト機（予備基板等）で今回の修正
一式を試し、様子が良さそうだと確認できてから2号機へも展開する、という
順序で進める。次にこの調査を再開する時は、まずテスト機での長時間backlog
試験（2号機と同じ`kBatchSeconds=15`・`kMaxRamBatches=3`設定で）から
始めるとよい。
