# batch-uplinkにTLS接続使い回しを実装し、v1.7.0へ追従する

[前回の調査](2026-08-08-device1-outage-and-deploy-drift.md)で「実装したい方向」として
合意した対策のうち、最優先だった接続使い回し（バックフィル中の連続TLSハンドシェイクが
ヒープ断片化・クラッシュの引き金になっている疑い）を実装した。

## 何をしたか

- `batch-uplink`側: `Uploader::postBatch()`が毎回ローカルで`WiFiClientSecure`/
  `HTTPClient`を新規に作っていたのを、`client_`/`http_`をUploaderのメンバへ昇格し
  `HTTPClient::setReuse(true)`で使い回すようにした
  （[batch-uplink#7](https://github.com/nna774/batch-uplink/pull/7)、マージ済み）。
  `HTTPClient::connect()`はソケットが生きていれば自動でハンドシェイクを省略する実装に
  なっている（ライブラリのソースを実際に読んで確認した）ので、呼び出し側の変更だけで
  済んだ。送るものが無くなったら`closeIdleConnection()`で明示的に閉じ、アイドル中に
  TLSセッション分のRAMを予約し続けないようにした。失敗時は`client_.stop()`で必ず
  繋ぎ直す。`sendAlert()`は宛先ホストが別（`alertUrl_`）なので対象外、従来通り
- `v1.7.0`タグを切ってpush
- Namazu側: `firmware/platformio.ini`の`lib_deps`と`terraform/build_lambda.sh`の
  `UPLINK_VERSION`を両方`v1.7.0`へ更新（CLAUDE.mdの既存ルール通り、片方だけ上げない）

## 確認したこと

- `firmware/`のesp32dev・adxl355両envで、実際に`https://github.com/nna774/batch-uplink.git#v1.7.0`
  を取得してのビルド成功を確認（タグ経由、ローカル参照ではない）
- `pytest lambda/tests`（98件）・`firmware/test/run.sh`（wire形式のバイト等価テスト）通過
- **実機device1へpull型OTAで配信し、本番デプロイまで完了した。** PR #32マージ後の
  masterから`tools/publish_ota.sh esp32dev`でfw_version `c891e89`を公開し、
  `tools/request_ota.py request 1 c891e89`で許可。約1分でdevice1が検知して自己更新、
  `fw_version`=`c891e89`・`pending_ota_version`=null（自動クリア）・`uptime_s`が
  再起動直後の値に着地し、`batches_total`も途切れず増加を確認した。**通常運用として
  正常に動くことは確認できたが、これが本来の狙い（バックフィル時にTLSハンドシェイクが
  実際に省略されるか、heap free/maxblockの推移がどう変わるか）の確認にはならない**。
  そちらは意図的に接続を切ってバックフィルを発生させないと再現しない、未確認のまま

## 次に何が可能になったか

`docs/design.md`「送信の信頼性」節の未定事項のうち、接続使い回し（第一候補）が
実装フェーズまで進んだ。証明書ピン留め(TODO)・タスク分割・`esp_reset_reason`記録
などの残りの未定事項は引き続き未着手。証明書ピン留めは別セッション（cloud routine）
に切り出そうとしたがGitHub未連携でルーティン作成に失敗しており、連携後に再度
着手が必要。
