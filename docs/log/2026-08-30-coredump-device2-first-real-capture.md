# coredump自動送信の初回実運用——device2から過去の実クラッシュを自動回収

PR #171(coredump自動送信のfirmware実装)をdevice2へOTA配信した直後、
起動からわずか18.5秒で`coredump/0002/a96e956-00001788017997149201.bin`が
S3へ自動アップロードされているのに気づいた。テスト用の意図的なパニックは
まだ仕込んでいなかった時点なので、これは**新firmwareの初回起動時に
ハードウェアのcoredumpパーティションへ既に残っていた、過去の実際の
クラッシュのcoredump**だと分かった——`captureIfPresent()`が設計通り
「見つけたら即座に確保・送信」した結果。

## fw_versionの食い違いに注意

S3キーは`a96e956`(今回OTAした**新**firmware)だが、`X-Namz-Fw-Version`ヘッダは
「アップロード時点で動いているfirmware」を送るため、実際にクラッシュした瞬間に
動いていたバージョンとは一般に一致しない。**OTAがクラッシュとアップロードの間に
挟まると必ず食い違う**——これは今回の設計の既知の制約として残る。
symbolizeする時はS3キーのバージョンを鵜呑みにせず、実際にクラッシュが
起きた時期のfw_versionを別途特定する必要がある(下記「このcoredumpの正体」参照。
OTA直前の`976bd93`とは限らない)。

## このcoredumpの正体（推定）

`976bd93`は[2026-08-29-device2-task-wdt-coredump-tls-handshake.md](2026-08-29-device2-task-wdt-coredump-tls-handshake.md)で
調査した、PR#163の事後解析中に見つけたのとまさに同じfw_versionである。
device2は`976bd93`のまま2026-08-29〜30にかけて約37秒の完全欠落を3〜13分おきに
繰り返していたと分かっている（`uploaderTask`が`WiFiClientSecure::connect()`の
TLSハンドシェイク待ちで20秒間WDTを養えず停止する既知の機構）。今回自動回収された
coredumpも、内容を読み解くまでもなく同じ機構によるものである可能性が高い——
PR #169/#170で対処した(batch-uplink v3.3.0、TCP接続/TLSハンドシェイク/
レスポンスヘッダ読み取りの各区間を3000msへ縮めて最悪合計を19秒→12秒にした)
のと同じ現象の生き残りだと考えられる。**新規の原因究明としてsymbolizeする
優先度は低い**——今回のOTAで対処版(`a96e956`、v3.3.0込み)が既に稼働しているため、
今後この頻度の欠落が収まるかどうかを実データで見る方が有益。

**ただし`976bd93`製という断定はできない。** coredumpパーティションは単一image・
次のパニックで上書きされる仕様なので、今回拾えたのは「device2がこれまでに
経験した最後のパニック」でしかなく、それが`976bd93`稼働中に起きた保証はない——
このcoredump機構自体が今回初めて実装されたものなので、`976bd93`より前の
もっと古いビルドで起きたパニックが、たまたま`976bd93`稼働中には(あるいは
その前の複数のOTA更新をまたいで)一度も新しいパニックで上書きされないまま
今日まで居座っていた、という可能性も残る。断定するにはcoredump自体が持つ
`app_elf_sha256`(esp-coredumpで抽出可能)と、過去にpublish_ota.shで配布した
各版のバイナリを突き合わせる必要がある——未実施。

## 今後の再起動について

「PR #174の修正(LittleFS未マウントバグ)をdevice2へ焼かないと、次に再起動したら
coredump機構が壊れるか」という問いには**否**——今回見つけたバグは
「コアダンプを一切見つけなかった起動で、かつキューに前回送り損ねた
ファイルが残っている」場合にだけ、そのファイルが永遠に取り残される
というもので、**新規のクラッシュを検出・送信する経路そのものは
`a96e956`(修正前)でも正しく動く**（`captureIfPresent()`は「見つけたら
mountする」ので、クラッシュ検出時は毎回ちゃんと動く。今回の自動回収も
実際に修正前のコードで成功している）。現在device2のキューは空
（回収したファイルは200 ACK後に削除済み）なので、今すぐ焼き直さなければ
ならない緊急性はない。ただし将来「クラッシュ直後のアップロードがネットワーク
不調で失敗する」ケースでファイルが取り残される可能性は残るため、
次回の定期OTA更新のタイミングでPR #174の修正込みの版に上げておくのが良い。
