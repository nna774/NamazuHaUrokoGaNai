# 1号機をブロックへ剛結し、机を叩いて傾き・相対方位を較正した

## 何を決めたか

1号機(IIS3DHHC)をブレッドボードごと（センサを外さず）2号機と同じコンクリートブロックへ
KPS-12アクリルフォーム両面テープで剛結し、両機を同時に机を叩いて加振した
（`0001-59541742`/`0002-59541742`、ともに`cloud_confirmed`で記録されたので
`flag_event.py mark`で人工地震フラグを立てて一覧を汚さないようにした）。

このイベントから傾き・相対方位を較正する [tools/calibrate_orientation.py](../../tools/calibrate_orientation.py)
を新規作成し、`namazu-devices`へ書き込んだ。

実測値: 傾き 1号機0.85°／2号機0.47°（どちらもほぼ水平）。相対方位は2号機を-7.9°回すと
1号機に一致（タップ直後±0.2〜0.5秒の窓でコヒーレンス0.98）。

## なぜ

[device_overlay.md](../device_overlay.md) §3.bで「2号機の本据え付けが前提」としていた
方位較正が、2号機の本据え付け完了・1号機の剛結完了で両方揃ったため着手した。

方位は重力DCだけでは決まらない（水平面内1自由度が不定）ので、人工加振の水平粒子運動の
主軸を両機で比較する方式(b)を採った。実装は:

1. 各機の静穏区間(onset前25秒)の重力DC平均から傾き（raw sensor frameでの重力方向の
   単位ベクトル`up`）を求める。
2. `up`から水平基底`h1,h2`を作る（raw frameのX軸を`up`に直交射影。upに近い時はY軸に
   切替。この手続き自体が決定的なので、同じ機体なら常に同じ基底になり較正のやり直しでも
   意味がぶれない）。
3. タップ直後の`h1,h2`成分に対し、基準機と対象機の間でラグ(検出タイミング差)と回転角を
   同時に探索するProcrustesフィットを行い、コヒーレンス最大の回転角を相対方位とする。

窓の取り方（タップ直後だけに絞るか、反響を含む数秒まで見るか）でコヒーレンスと角度の
安定性が変わることを確認した。±0.2〜0.5秒（立ち上がり直後）が最も安定し
コヒーレンス0.98、±0.5〜3秒まで広げると反響が乗ってコヒーレンス0.74まで落ちる。
これを踏まえ、既定の解析窓を±0.2〜0.5秒に固定した。

## 何が覆ったか

計算の途中、傾きの角度計算で`np.degrees()`を二重に掛けるバグを踏んだ
（1号機の傾きが一時48.95°と出て「そんなに傾いているわけがない」と気づいて修正、
正しくは0.85°）。ラグ0の相関係数だけで方位を決めようとした時も、時間軸の単位を
秒とマイクロ秒で揃え忘れていて全ラグで係数1.000という明らかにおかしい値が出た
（データがどのラグでも同じ2サンプル付近しか参照していなかった）。両方とも
「値が明らかに物理的におかしい」ことから気づけたので、こういう解析コードは
必ず一度、常識と比較して検算すること。

## 次に何が可能になったか

- `namazu-devices`の`tilt_up`/`tilt_deg`/`azimuth_deg`/`calibration_ref_device`/
  `calibrated_at_us`/`calibration_events`が書き込まれ、`--write`で毎回全体上書きできる
  ので、据え付けを直したりデータが増えたりしたら同じコマンドで叩き直せる。
- ダッシュボード側での活用（方位不変モード表示、N/E/UDでの重ね描き）はまだ未着手
  ([device_overlay.md](../device_overlay.md) 未決事項)。
- 絶対方位(真の北)はまだ決まっていない。相対値だけ。絶対方位が要る時は実イベントの
  P波初動を使う方式が残っている。

pytest(`tools/tests` + `lambda/tests`) 167件通過（`tools/tests/test_calibrate_orientation.py`を
新規追加、合成データで傾き0・既知の回転角・既知のラグを正しく復元できることを確認）。
