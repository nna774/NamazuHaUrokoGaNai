# HTTPSプル型OTAの作戦を検討した（実装は未着手）

`ota.md`のLAN内push型（2026-08-06実装）に続き、外出先からの更新・無人運用に要る
プル型の作戦だけをまとめた。実装はしていない。

## 決めたこと

- **トリガーは「手元から明示許可」方式を採用する。** デバイスが定期的に自律
  ポーリングして黙って最新へ追従する方式は不採用。理由: 配布物（S3/CloudFront上の
  bin）の書き込み権限が万一侵害された場合、無人運用中の全機へ運用者の操作なしに
  コードが流し込める経路になり、push型より一段階ブラスト半径が大きいと判断した
  （ユーザーに選んでもらった上での決定）。
- 伝達経路は[リモート再起動](../remote_restart.md)と同型（バッチ送信レスポンスへの
  便乗）を踏襲する。ただし**再起動要求と違い、返した直後に値をクリアしない**。
  OTAターゲットは「あるべき状態」なので照合し続けてよく、これがそのまま
  ダウンロード/書き込み失敗時のリトライ機構になる。
- 配布物は新規ドメイン/ACM証明書を作らず、既存ダッシュボードのCloudFront+S3に
  `ota/<env>/<version>.bin`として相乗りする。
- ロールバックは push型では「期待しない」と割り切ったが、pull型は無人トリガーで
  現地対応できない期間が長くなりうるため、`CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE`
  を有効化する価値が初めて出ると判断した（bootloader設定なのでpush型にも効く）。

## 何が覆ったか

特になし（新規の作戦立案）。ただしpush型ota.md §5「ロールバックは期待しない」は、
pull型実装時に前提が変わる可能性がある旨を明記した。

## 次に何が可能になったか

- `docs/ota.md`§7に作戦を書いた。未決事項（サーバがデバイスの現在バージョンを
  知る手段が無い、`Uploader`の複数ヘッダ監視拡張、段階的ロールアウトの表現）を
  洗い出し済みなので、次は実装フェーズに進める。
- ビルド時のgit短縮hash埋め込み（`NAMZ_FW_VERSION`）は`memo.md`の残タスク
  「起動ログにバージョン/hashを出す」とも合流するので、実装時に一緒に片付けられる。

詳細は[ota.md §7](../ota.md#7-将来-httpsプル型作戦実装は未着手)を参照。
