# coredumpにクラッシュ時刻を持たせる

2026-10-28、device2が21:43頃から送信できなくなり(TLS接続で詰まりTASK_WDTパニックを
繰り返したと見られる)、ユーザーのボタン再起動後にcoredumpが2本まとめてS3へ届いた。
どちらも回収時刻は21:54:44〜46で、いつクラッシュしたかは21:43〜21:53の間としか
絞れなかった。dump自体に壁時計は無く(gdbで`xTickCount`も読めない)、
`handler.py`の「回収時刻≒クラッシュ時刻」という前提は、回線が死んでいてアップロード
が遅れる時にまさに崩れる。

## 決めたこと

- uploaderTaskが毎周RTC memory(`gRtcLastAlive`)へ壁時計を書く。WDTリセットでも
  残るので、次回起動の`setup()`が前回の最終生存時刻として読める。読んだらすぐ無効化し、
  今回の起動の値と混ぜない。
- 時刻はdumpのファイル名に埋める(`<seq>-<crash_at_us>.bin`)。サイドカーファイルに
  しなかったのは、キュー列挙が全ファイルをdumpとして扱うのと、dumpと時刻の
  対応が1ファイルで原子的に保たれるため。クラッシュループでキューに複数溜まっても
  dumpごとに別の時刻を送れる(既存のpump-traceヘッダは直近1回分の一発送信)。
- ingestは通知に「クラッシュ推定時刻」を足し、S3メタデータにも`crash-at-us`を残す。
  S3キーの時刻は従来どおり受信時刻のまま(キー形式を変えると既存の取得手順が崩れる)。

## 限界

- NTP未同期で落ちた起動は時刻0で、ヘッダを付けない。
- dumpのコピーに失敗してハードウェア側に残り続けた場合、次の起動で取る時刻は
  「その次の起動」のものになり、1起動ぶんずれる。
- 「最終生存」はuploaderTaskの周回単位なので、pump()で詰まったクラッシュは
  詰まり始めの時刻(+WDT秒数が実際のクラッシュ時刻)になる。
