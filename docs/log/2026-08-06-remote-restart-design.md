# 2026-08-06 リモート再起動 設計をまとめた

## 何を決めたか

コマンドラインから再起動要求を送り、デバイスがバッチ送信時に検知して自分で
再起動する機能の設計を [docs/remote_restart.md](remote_restart.md) にまとめた
（実装はまだ・今回は設計のみ）。

伝達経路は「バッチ送信レスポンスへの便乗」を採用。専用の軽量ポーリングエンドポイントを
別途立てる代案もあったが、memo.md の要望（送信のたびに確認したい）に素直な形を選んだ。

## なぜそう決めたか

現状の `Uploader::postBatch`（batch-uplink）は HTTP ステータスコードしか見ておらず、
レスポンスヘッダ・ボディを一切読んでいない。便乗案を採るなら batch-uplink 自体の改修が
要る。CLAUDE.md が警告する「向こうのための変更が黙って混入する」リスクを踏まないよう、
2026-08-05 の spill overflow 対応で実際に使った**オプトイン方式**
（[log/2026-08-05-device2-spill-overflow.md](2026-08-05-device2-spill-overflow.md) の
`dropOldestWhenFull`）を踏襲する設計にした。「再起動」という意味づけは batch-uplink 側に
持たせず、「指定ヘッダを1つ読んで返す」汎用APIとして実装し、解釈は `main.cpp` 側に置く。

再起動要求の状態は `namz-devices`（batch-uplink `devices.py`）に持たせ、
`tools/flag_event.py` と同型の CLI で立てる方針にした。既存の運用パターン
（生存台帳・手元CLIでのDynamoDB直更新）をそのまま流用でき、新しい仕組みを増やさずに済む。

一回性（ACK）はレスポンス送出直後にサーバ側でフラグを消す割り切りにした。厳密な
往復ACKも検討したが、取りこぼしても実害は「手元でもう一度要求を立て直すだけ」なので
過剰と判断した。
