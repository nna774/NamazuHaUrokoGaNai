# 2026-09-06 イベントに事後解析の判定(verdict)を持たせる

## きっかけ

事後解析で昇格したイベントが既定一覧を占めている（実測: 既定一覧33件中、`cloud_confirmed`は
4件だけで残り29件が手動昇格）ことから、「埋没イベントを一覧から隠す`hidden`フラグ」を提案した。
ユーザーから**「hiddenは名前がよくない。『オートジャッジした』かつ『埋没』とかが条件ならわかる。
今は手動イベントに判定が入ってないが、これを入れると良かったりする？」** と返り、
そちらが正しいと判断して設計を変えた。

## 何を決めたか

- **イベントに`verdict`（`good`/`warning`/`critical`）と`verdict_source`（`human`/`auto`）を
  持たせる。** 語彙は`tools/detection_events.csv`のverdict列と同じものを使う（語彙を分けると
  対応表が要る）。
- **一覧の既定フィルタは変えない。** 埋没と判定したイベントも既定で出す。
- `flag_event.py verdict / unverdict`、`promote_event.py --verdict`、api の `/event`・`/events`
  がフィールドを返す。ダッシュボードの見せ方（バッジ）はユーザーが手元で眺めてから決める。
- 手順書を「**判定に関わらず必ず昇格する**」に変え、手順3.5を「CSVとイベントの2箇所に
  同じverdictを書く」に変えた。

## なぜ`hidden`をやめたか

`hidden`は**結論を直接持たせるフラグ**で、なぜ隠れるのかがデータから読めない。事実
（判定・誰が判定したか）を持って表示は導出する方が、後から方針が変わっても1行で切り替わる。
実際、隠す条件を「verdictだけで決める」「`verdict_source == "auto"`の時だけ隠す」の
どちらにするかは、フィルタ1節の差でしかなくなった。

## なぜ隠さないことにしたか

数字を見たら前提が崩れた。既定一覧は1ヶ月で33件（約1.7ページ）、うち`cloud_confirmed`は
**4件だけ**。埋没を隠すと一覧は10件程度まで落ちる——見やすくなるのではなく**空になる**。

そもそも「調べたが埋没だった」は「まだ調べていない」と区別されるべき結論で、この
プロジェクトは検出限界を測ること自体を目的の一つにしている。隠すとその区別が消える。
また`docs/log/`はevent_idでイベントを参照しており、隠すと読者は「全件表示」を押すことになるが、
あの表示には`checked`のみ44件と人工地震22件も混ざるので探す場所として機能しない。

**本当の問題は件数ではなく、行が全部同じ顔で震度0にしか見えないこと**——つまり描画の問題だった。
verdictを持たせてバッジで出せば、一覧は「何を調べて、何が見えて、何が見えなかったか」の
記録として読める。

## 隠す判断が要るのは機械が陰性を保存し始めた時

別途設計中の「地震候補の定期スキャンと一次判定」（未マージ）が陰性まで自動保存するようになれば月30件が
積み上がる。その時に`verdict_source == "auto"`で絞ればよく、そのためのフィールドは今回
入れてある。**今は絞らない。**

## 実装メモ

- `events.py`に`VERDICTS`定数・`set_verdict()`・`record_manual_event(..., verdict=)`。
  検証（未知の値でValueError）を通す。
- `flag_event.py`と`promote_event.py`は`common.events.VERDICTS`をimportして語彙を共有する
  （`flag_event.py`にはこれまで`lambda/`へのsys.path追加が無かったので足した）。
- テストの`_FakeTable.update_item`が`#n`1個しか扱えなかったので、複数の名前・値プレースホルダを
  扱える形に一般化した（`SET #v = :v, #s = :s`と`REMOVE #v, #s`のため）。

## 実施した運用作業

- **既存34件へverdictをバックフィル**（good 19 / warning 7 / critical 8、全て`source=human`）。
  `detection_events.csv`の判定と手で紐付けた。
- **`detection_events.csv`にあるのにイベントが無かった5件を昇格**（新しい手順書の
  「判定に関わらず必ず昇格」に合わせた遡り適用）: 福島県沖M4.0(07-24)・福島県沖M4.5(08-26)・
  茨城県南部M3.4(08-26)・福島県中通りM3.3(08-31)・宮城県沖M3.8(09-04)。**07-24のdevice2だけは
  rawが無く昇格できない**——ADXL355(device2)の導入前だったため。残り4件は`relate`済み。
- **Lambdaをデプロイ**（`common/`を触ったので ingest/detect/api/watchdog の4関数が更新。
  planは`0 to add, 4 to change, 0 to destroy`）。`/events`・`/event`がverdictを返すのを実機で確認。

## CloudFront invalidationを打っていない（既知の副作用）

**ユーザー判断で今回は見送った。** `/event`は波形付きイベントを`max-age=365日`で返すため
（`EVENT_CONFIRMED_CACHE_S`、`manual`イベントも同じ経路）、**今日より前に一度でも取得された
event_idの詳細は、キャッシュが切れるまでverdictを含まない応答を返し続ける**。
一覧(`/events`)はキャッシュしていないので即座に反映される。ダッシュボードのバッジを
既存イベントで確認したくなったら、その時に34件ぶんの`/event?id=<eid>`を列挙して打てばよい
（ワイルドカードは使わない）。

## ダッシュボードの表示

案を5つ（震度セルにバッジ / 判定の専用列 / 行頭のアクセントバー / 「手動」タグの扱い違い）
実データで並べたスクラッチをローカル配信して選んでもらい、**「判定」専用列（案B）**を採用した。

- 列は `機` と `震度` の間。色ドット＋「検出/微妙/埋没」、未判定は「—」。
- 色は既存の語彙に合わせた（検出=手動タグと同じteal、微妙=amber、埋没=人工地震タグと同じグレー）。
- **狭い画面(≤700px)では `継続` 列を隠す**。列を1つ足したぶんを1つ落として、モバイルの
  列数を従来と同じに保つ（`#devices-table` が累計バッチ・版数でやっているのと同じ手）。
  継続はイベント詳細で見られるし、手動昇格イベントでは常に0sで情報量が薄い。
- 「検出」「埋没」が1文字ずつ縦に割れたので判定列は `white-space: nowrap`。
- **狭い画面では発生時刻を日付/時刻の2段に割る**（`.ymd`/`.hms`、`≤700px`でのみ`display:block`）。
  ブラウザ任せの折り返しだと列幅が「2026/9/6 14:17:28」1行ぶんで見積もられ、右側に
  使わない余白が残っていた。空いた幅は震度セルへ回る。広い画面は従来どおり1行。
- **`人工地震`タグを`人工`に詰めた**（正式名称は`title`とイベント詳細に残る）。狭い画面で
  震度セルが3段になり、人工地震の行だけ極端に背が高くなっていたため。`.badge`全体にも
  `white-space: nowrap`を入れ、語の途中で「人工地/震」と割れないようにした。
- **`手動`タグは判定が付いていない時だけ出す。** 判定列がある以上「人が調べた」ことは
  そちらが示すので冗長で、狭い画面では震度セルが2段になる原因でもあった。実効幅573px
  （実機430px×ブラウザ表示75%）で見比べて決めた。
- **行は薄くしない。** verdictで隠さないのと同じ理由（埋没も等しく読める記録として残す）。
