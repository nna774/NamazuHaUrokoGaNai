# batch-uplink v1.1.0 への追従と、マージ漏れの修正

device2のflash_size修正PR(#4)がマージされた後の後始末。batch-uplink側のPR(#1)も
マージされたのでタグを切り、Namazu側を追従させた。その過程で、直前のPRマージに
本来含まれるべきコミットが1本漏れていたと分かった。

## 何を決めたか

- batch-uplink に `v1.1.0` タグを切った（`Uploader`の`dropOldestWhenFull`オプトイン追加、
  後方互換のマイナーバンプ）。
- Namazu側を追従: `firmware/platformio.ini`の`lib_deps`と`terraform/build_lambda.sh`の
  `UPLINK_VERSION`をどちらも`v1.1.0`に更新。
- `firmware/src/main.cpp`の`Uploader`生成に`dropOldestWhenFull=true`を明示的に渡した。
  device2は16MB化で168.8分の余裕ができたが、それでも溢れた場合はRAM無制限積み増しで
  クラッシュするより、最古のデータから捨てて動き続ける方を選ぶ。
- **マージ漏れを発見して直接修正した**: PR#4のマージ済みコミット(`f279940`)には
  `board_build.flash_size`のバグ修正コミット(`904395d`)が含まれていなかった。
  masterには起動ループの原因そのものが残っていたため、`904395d`を新しいブランチに
  cherry-pickしてこのPRに含めた。

## なぜそう決めたか

- PR#4のマージ時刻(`f279940`、2026-08-05 19:16:20 JST)と、修正コミット`904395d`の
  作成時刻(19:42:58 JST)を比較すると、**修正コミットはPRマージの26分後に該当ブランチへ
  pushされていた**。マージ操作自体はブランチのその時点のHEAD(`59d6dfb`)を取り込んだので、
  後から積んだコミットは自動では拾われない。GitHubのPRは「マージボタンを押した時点の
  HEAD」を取り込むのであって、ブランチの以後の更新を追従しない。
- 実機(device2)は`904395d`を直接書き込んで動いているので現物は無事だが、**gitのmasterを
  信じて誰かが`env:adxl355`を再ビルド・別の個体に書き込むと、直っていない
  `board_build.flash_size`のバグを踏んで起動ループする**。実機の状態とリポジトリの状態が
  食い違ったまま放置するのは危険なので、他の作業より優先して直した。

## 発見された制約

- **PRの作業ブランチへのpushは、マージ後は捨てられる。** 「最後にpushしたコミットは
  自動的にPRに乗っている」という思い込みは成立しない。マージ直前に
  `git log origin/<branch>..HEAD`やPRのdiffで「今からマージされる内容」を確認する
  習慣が要る。特に、実機検証などマージ操作と並行して進めがちな作業がある時は要注意。

## 次に何が可能になったか

- batch-uplinkの`dropOldestWhenFull`が実際にfirmwareへ配線され、次に device2 を
  再ビルド・書き込みする時から有効になる（現在稼働中のバイナリはまだ古い版なので、
  次回の書き込み機会に反映される）。
- device1のflash_id確認は引き続き未着手（TODOのまま）。
