# ダッシュボードのライブ表示に、クライアント側の概算震度を追加した

## 発端

`memo.md` に「ダッシュボードの表示、ガル(加速度)表示になっているけど、ダッシュボードの
クライアントだけで震度表示にもできるようだったら追加してほしい。バケットを見まくらないと
いけない とかなら作戦を考える」とあった。

## 調査結果: 「追加リクエストなし」では不可能、ただしS3走査は増えない

- `/recent` は `MAX_POINTS`(当時3000) を超えると min/max envelope に間引いて返す
  (`lambda/api/handler.py` `_waveform_payload`)。ライブ画面の既定窓「1分」は
  100Hz×60秒=6000点で、間引き前から既に3000を超えていた。**つまり最短の窓ですら
  クライアントに届く時点でenvelope化されており、震度計算に要る生サンプルが無い。**
- 一方、S3読み出しコストはこの間引きと無関係。`store.load_window` はその窓の生バッチを
  最初から全部S3から読んでおり(`list_raw_keys_in_range`→`get_batch`)、`MAX_POINTS`は
  レスポンスを軽くするための後段の処理でしかない。**「バケットを見まくる」心配は当たらない。**

この2点をユーザーに提示し、`MAX_POINTS` を6000(=1分@100Hz)へ上げて1分窓をrawのまま
返す方針で進める指示を得た（3分以上の窓は従来どおりenvelope）。

## 実装

- `lambda/api/handler.py`: `MAX_POINTS` を 3000→6000 に。S3スキャン量は `minutes`
  パラメータ(上限30分)で決まりこれとは無関係なので、増やしてもスキャンは増えない。
- `dashboard/app.js`:
  - `tools/jismo/realtime.py` のオフライン一括計算(`filtered_composite`)と同じ手順を
    JSに移植（FIRで3軸畳み込み→ベクトル合成→整定時間を捨てる→超過時間0.3秒のa0→
    気象庁丸め）。FFT版(`jma_fft.py`)ではなくFIR版を選んだのは、FFTだと非2^n長(6000点)の
    離散フーリエ変換をJSで自前実装する必要があり、既にfirmwareが同じ目的で使っている
    FIR係数（511tap、`firmware/lib/Shindo/JmaFirTaps.h`と同一値）をそのまま埋め込む方が
    実装量・検証コストとも小さいため。
  - ゼロ初期履歴で畳み込むため先頭に整定時間の過渡応答が乗る。streaming版の
    `_warmup`(numtaps+fs秒)と同じ考え方で先頭を捨ててから計算する。ライブは連続する
    履歴を持たない単発の60秒窓なので、この間は「本来なら履歴側にあったはずの60秒」の
    うち先頭約6.1秒を諦める形になる（実用上は許容範囲と判断）。
  - `EVENT_RAW_MAX_POINTS`（イベント詳細のズームraw取得しきい値）もAPIと同じ6000に同期。
  - ライブ画面に `#live-intensity` を追加し、「1分」表示(`wf.mode==='raw'`)かつ非ズーム時
    のみバッジを出す。3分以上・拡大表示・データ不足時はその旨を薄く表示。
- `dashboard/index.html`: `#live-intensity` の要素と、概算値である旨の注記を追加。

## 検証

- Python側(`jismo.realtime.RealtimeIntensity`)で合成地震(静穏+2Hz正弦波の擬似イベント)
  60秒分を計算し、期待値(計測震度3.5・震度4)を確定。
- 同じ入力をNode.jsで`app.js`から関数を切り出して実行し、**完全一致**（intensity=3.5,
  scale='4'）を確認（taps配列はテキスト化で有効9桁に丸めているため a0 の下位桁のみ
  無視できる差）。
- ヘッドレスChromeでダッシュボードを実際にレンダリングし、上記合成波形を返すスタブAPI
  経由でバッジ表示（「概算震度 4 計測震度 3.5」）を確認。本番API（未デプロイのため
  `MAX_POINTS`はまだ3000のまま）に向けた場合は「表示範囲が広いため計算できません」に
  正しくフォールバックすることも確認。
- `pytest lambda/tests`: 97件通過（`MAX_POINTS`変更後も無改修で通過）。

## 残作業

- **未デプロイ**（`terraform apply` と dashboard の S3 sync/invalidation はこの作業に
  含まれていない）。デプロイ後、本番の1分窓で実データの概算震度がイベント一覧の確定値と
  近い値になるか実機データで確認するとよい。
- FIRのnumtaps/fsを変更したら `dashboard/app.js` の `JMA_FIR_TAPS` を手動で再生成すること
  （自動同期の仕組みは無い。firmwareの `JmaFirTaps.h` も同様に手動生成)。
