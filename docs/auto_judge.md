# 地震候補の定期スキャンと通知

**「気象庁の地震一覧を定期的に見て、事後解析すべき候補をSlackに知らせる」** 仕組み。
2026-09-08にコード実装済み（`lambda/quake_scan/`・`terraform apply`は未実行、
実機ではまだ動いていない）。**判定・保存は自動化しない**——機械がやるのは
「候補への気付き」まで。実装の詳細は
[log/2026-09-08-quake-scan-implementation.md](log/2026-09-08-quake-scan-implementation.md)。

## なぜやるか

**手で拾う限り取りこぼす。** 実例が2つある:

- 2026-09-04 16:45 福島県沖M4.0は「投げる価値あり(境界帯)」だったのに誰も気付かず、
  2日後の棚卸しで見つかった（[log/2026-09-06-fukushima-oki-m4.0-post-hoc-detection.md](log/2026-09-06-fukushima-oki-m4.0-post-hoc-detection.md)）。
- 2026-08-21〜08-30の4件が`detection_events.csv`に長期間追記されないまま埋もれていた
  （[log/2026-09-02-backfill-detection-events-csv.md](log/2026-09-02-backfill-detection-events-csv.md)）。

いずれも「思い立った時に気象庁の地震一覧を手で眺めて拾う」運用に依存していたことが原因。
**自動化する価値があるのはここ（気付き）であって、事後解析そのものではない。**

## 検討の経緯（詳細は各ログへ）

当初は「候補の解析まで自動化し、一次判定が陽性なら波形も自動保存する」設計
（`detectlab.analyze()`をSTA/LTA・SNR・機間相関で自動判定する案）を検討したが、後退させた。

理由: [docs/post_hoc_detection.md](post_hoc_detection.md)の手順どおり実際に判定した事例を
見返すと、verdictの判断が数値の閾値には落とし込めない対話的な推論だと分かったため。
青森県東方沖M4.7では「device2(ADXL355)の方が高感度だから片方だけの閾値超過は期待される
姿」という理屈まで込みでようやく`good`に落ち着いている
（[log/2026-09-06-aomori-touhou-oki-m4.7-post-hoc-detection.md](log/2026-09-06-aomori-touhou-oki-m4.7-post-hoc-detection.md)）。
ここを機械の閾値判定で代替すると、粗い判定しか出せない上に人間が結局全部読み直すことに
なり、自動化の効果が薄い。

そこで**「機械にできるのは候補への気付きまで」と割り切り、判定・保存は今までどおり
[docs/post_hoc_detection.md](post_hoc_detection.md)の手順で人間（とセッション上のやり取り）が
行う**設計に絞った。数値サマリの永久保存・一次判定条件・自動昇格の可否・独自保存パスの
是非は、この絞り込みにより論点として消滅している。

対象の選定条件（下記）を詰める過程で「遠すぎ」ゾーンのマグニチュード閾値を何度か
見直している。詳しい検討経緯は
[log/2026-09-08-auto-judge-narrowed-to-scan-notify.md](log/2026-09-08-auto-judge-narrowed-to-scan-notify.md)。

## 方式

1. 日次でEventBridgeがLambdaを起動する。
2. `list.json`を取得し、`scan_quakes.py`と同じ基準（下記「対象」）で候補を絞る。
   窓は実行間隔より広め(28時間)に取る（詳細は「重複排除」）。
3. 候補のうち、まだ通知していない`eid`をまとめて**1日1通のSlackダイジェスト**として通知する
   （詳細は「通知フォーマット」）。
4. 通知したeidと成功実行時刻をDynamoDBに書く。

**解析・判定・保存はしない。** 通知を見た人間が、その日の候補をまとめてセッションに投げ、
従来どおり[docs/post_hoc_detection.md](post_hoc_detection.md)の手順で事後解析し、必要なら
`promote_event.py`で保存する。

## 対象（選定条件）

`zone_of()`（[tools/detection_range.py](../tools/detection_range.py)）の3ゾーン判定を使い、
ゾーンごとに扱いを変える:

- **「投げる価値あり」「近すぎ」は全件通知する。**
- **「遠すぎ」はマグニチュード4.0以上だけ通知する。**

3ゾーンの判定自体は`scan_quakes.py`と同じだが、**遠すぎに対するマグニチュード閾値は
`scan_quakes.py`のCLIオプション（`--all`は近すぎの表示可否のみ）では表現できない新しい
選別ロジック**。`detection_range.py`に定数として1箇所にまとめ（下記「実装」）、
`scan_quakes.py`・このLambdaの両方から参照できるようにする。

### 閾値4.0の根拠

**「浦河沖M6.0(645km)・熊本M7.1(869km)がレンジ外でprobableだった」という当初の根拠は、
今の回帰式では成り立たない**——事後解析の実例が増えて回帰の予測レンジが広がった結果、
この2件は現在「投げる価値あり」ゾーンに入っている（`detection_events.csv`で検算済み）。
つまり最初にこの仕組みを検討するきっかけになった2つの実例は、実はもうこの閾値の対象外だった。

`detection_events.csv`を現在の回帰で判定し直すと、「遠すぎ」ゾーンに実際に該当する事例は
5件しかなく、成功（`good`）は青森県東方沖M4.7（548km）の1件のみ。マグニチュード・
境界超過の倍率のどちらで見ても、この1件と他の埋没事例（M3.5〜M4.6）を綺麗に分ける軸は
見つからなかった——n=5では閾値の精密な最適化はできない。

直近30日の実測（2026-09-08時点）:

| ゾーン/閾値 | 件数/月 |
|---|---|
| 投げる価値あり（全件） | 20 |
| 近すぎ（全件） | 5 |
| 遠すぎ M≥3.0 | 124 |
| 遠すぎ M≥3.5 | 76 |
| **遠すぎ M≥4.0（採用）** | **40** |
| 遠すぎ M≥4.5 | 15 |
| 遠すぎ M≥5.0 | 4 |

M3.0未満まで広げると九州の群発地震（M1.7〜3.0が大半）が月100件以上流入する。これは
「取りこぼしを避けるために広く取る」の範囲を超える——震源距離(~900km)に対してこの
マグニチュード帯は**物理的にほぼ確実に検出不能**で、拾っても情報量がほぼゼロのまま
セッションの調査対象だけが膨らむ。M4.0は「唯一の成功例(M4.7)に対して多少の見逃しリスクを
許容しつつ、無意味な群発を再流入させない」バランス点として選んだ。

**この閾値はn=5の実例に基づく暫定値であり、実例が増えるたびに見直す前提。** 「閾値の
定期見直し」（下記）で毎週思い出せるようにしている。

## 重複排除（広めの窓＋ステートフル）

日次実行の間隔ぴったりの窓だと、実行時刻のブレ（Lambdaの遅延・リトライ）で境界の候補を
取りこぼす恐れがある。**取りこぼしの方が実害が大きい**（このドキュメントの発端そのもの）
ので、窓は実行間隔（24時間）より広め（**28時間**）に取り、重複は状態で吸収する。

- DynamoDBに小テーブル（`namazu-quake-scan`案）を新設し、**通知済み`eid`の集合**と
  **最後に成功実行した時刻(`last_success_at_us`)**を持つ。
- 毎回、候補のうち通知済みでないものだけ通知し、通知したeidを追記する。
- 1回落ちても、次回の広い窓が自然に拾い直す（自己修復）。
- 突き合わせに使うのは気象庁の`eid`そのもの（`scan_quakes.py`が同一`eid`の複数報を
  最新のもの1件に既にまとめている）。namazu独自のevent_idのようにonset時刻由来で
  はないので、気象庁側の発生時刻改訂で別idになる問題は起きない。

## 失敗検知

**窓を広げても、実行そのものが起きなければ意味がない。** ジョブの外から見る必要があり、
`watchdog` Lambdaに1ブロック追加する。`watchdog`自体はデバイス単位でループしながら
`devices.py`/`ota_watch.py`の`evaluate()`系関数を呼ぶだけの実装で、汎用フレームワークが
あるわけではない——`ota_watch.py`（pull型OTA停滞監視）が後から同じ流儀で足された前例に
倣い、新モジュール（`evaluate_stuck()`的な純粋関数＋`mark_notified`/`clear`）を追加する形で
`last_success_at_us`のstalenessを見る。日次のはずなのに**32時間**動いていなければSlack通知する
（重複排除の窓28時間より一段広く取り、「本当に動いていない」と確信してから鳴らす）。

ジョブ内部でのエラー（`list.json`取得失敗等）は別途`try/except`で捕まえて即座に通知するが、
**ホストごと死んだ・呼び出されなかった場合はジョブ自身では検知できない**ため、この
外側からの失敗検知が本質的に必要になる。

## 通知フォーマット（1日1通のダイジェスト）

候補ごとに別々のSlackメッセージを送ると、「遠すぎ」を広めに取った日に1日5件前後届く
ことになる。**個別送信ではなく、その日の新規候補をまとめて1通のダイジェストにする。**
候補が0件の日は「新規候補なし」の一言で済ませる。

これは通知疲れ対策であると同時に、実際の運用形態（その日の候補をまとめてセッションに
「これを調査して」と投げる）に合わせた形でもある——1通にまとまっていれば、そのまま
セッションに貼るだけで済む。

各候補のブロックは`scan_quakes.py`の出力形式をそのまま流用する:

```
[2026-09-04T16:45:00+09:00] 福島県沖  M4.0  震源距離123km（レンジ80〜160km）  最大震度3  → 投げる価値あり
  detectlab.py --at "2026-09-04 16:45" --eew "37.3,141.2,40,2026-09-04 16:45" --minutes 10 --device 1 2
```

`--eew`の中身（緯度・経度・深さ・発生時刻）は[docs/post_hoc_detection.md](post_hoc_detection.md)
手順0の入力そのものなので、新しいフォーマットを考える必要はない——`main()`内の整形部分を
関数に切り出し、CLIとLambda通知の両方から呼ぶ。

**新規候補が0件でない時は、本文の頭にメンションを付ける**（`watchdog`の欠測通知と同じ
考え方・同じ宛先）。Incoming Webhookはスレッド返信ができない（`ts`を返さず常に新規
メッセージになる）ので、「見逃されたら困るものを目立たせる」目的は返信ではなくメンション
で果たす。0件の日（「新規候補なし」）にはメンションを付けない。

## 閾値の定期見直し（毎週土曜日にリマインド）

「対象」節の閾値（M≥4.0）はn=5の実例に基づく暫定値で、実例が増えるたびに見直すべきもの
だと明記した。とはいえ、明記しただけでは誰も思い出さずに放置されるのが常なので、
**仕組み自体にリマインドを埋め込む。**

毎週**土曜日**のダイジェストには、候補の有無に関わらず「そろそろ閾値を見直してもいいかも
（M≥4.0・重複排除の窓28時間・失敗検知32時間は`detection_range.py`の定数、実例が増えた
かは`detection_events.csv`を見よ）」という一言を追記する。JSTの曜日判定
（`datetime.now(JST).weekday() == 5`）だけで済み、新しい状態管理は要らない。

## 実装

`detect`/`ingest`と同じ骨格。新しいアルゴリズムは無く、既存のロジックの移植・共有化。

- 新規Lambda関数`lambda/quake_scan/`＋`terraform/lambda.tf`にEventBridge日次ルール
  （`watchdog`と同じ形の`aws_lambda_function`/`aws_cloudwatch_event_rule`/
  `aws_cloudwatch_event_target`/`aws_lambda_permission`）＋DynamoDBテーブル新設
  （`namazu-quake-scan`、状態管理は`lambda/common/quake_scan.py`）。
- `tools/detection_range.py`に`FAR_BUT_NOTABLE_MAG = 4.0`と、ゾーン＋マグニチュードから
  「通知すべきか」を返す`worth_notifying(zone, magnitude)`を追加。`scan_quakes.py`と
  Lambdaの両方がこれを呼ぶことで、閾値が2箇所に分散するのを防ぐ。
- `hypocentral_km`/`bearing_deg`/`parse_station`/`DEFAULT_STATION`を`detectlab.py`
  （scipyに依存）から`tools/station.py`（math/osのみ）へ切り出した。これで
  `scan_quakes.py`・`detection_range.py`はscipyを持ち込まずにLambdaへ同梱できる。
- `scan_quakes.py`の候補整形部分を`format_candidate()`に切り出し、CLI出力と
  Lambda通知のSlackダイジェストで共用する。
- `watchdog/handler.py`へ失敗検知の1ブロックを追加（デバイスループの外、
  `quake_scan.evaluate_stuck()`を1回だけ呼ぶ）。
- `terraform/build_lambda.sh`の`build_one()`に、tools/直下のファイルを追加同梱する
  引数を足し、`quake_scan`だけ`scan_quakes.py`・`detection_range.py`・`station.py`・
  `detection_events.csv`を同梱する。

**実装のみ完了、`terraform apply`はまだ実行していない**（実データでの動作確認はこれから）。

## コスト

数値サマリ・波形の自動保存を一切しないので、以前検討していたストレージコストの心配は
消えている。発生するのは`list.json`の日次GET（気象庁側、無料・認証不要）とDynamoDBの
少量の読み書きだけで、無視できる規模。

## 決定事項のまとめ（実装時のパラメータ）

| 項目 | 値 |
|---|---|
| 実行頻度 | 日次（EventBridge、Lambda） |
| 対象ゾーン | 投げる価値あり・近すぎは全件、遠すぎはM≥4.0のみ |
| 重複排除の窓 | 28時間（実行間隔24時間+4時間） |
| 失敗検知のしきい値 | 32時間 |
| 通知形式 | 1日1通のダイジェスト（`scan_quakes.py`と同じブロックを候補ごとに並べる） |
| 閾値見直しリマインド | 毎週土曜日のダイジェストに一言追記 |

コードは実装済み（`git grep quake_scan`で追える）。残っているのは`terraform apply`
での実デプロイと、実データで数週間回した上での閾値の検証・見直しのみ。
