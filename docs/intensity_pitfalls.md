# 計測震度の落とし穴（窓とドリフト）

2026-08-02、ADXL355 の立ち上げで静穏データを `tools/backtest.py` に掛けたところ、
**静止しているのに計測震度 2.1**（`a0=3.9gal`）が出た。原因を切り分けた記録と、
その結果入れた修正。センサとは無関係の、**震度算出側の問題**だった。

## 1. FFT版とFIR版は「窓」が違う（これは仕様。バグではない）

同じ計測震度でも2つの実装は測る区間が違う。

| | 区間 | 出るもの |
|---|---|---|
| `jismo/jma_fft.py`（正式） | **渡した記録の全体**を1つの窓として扱う | 震度が1個 |
| `jismo/realtime.py`（FIR） | **60秒の移動窓** | 各時点の震度。`backtest.py` はその最大を表示 |

したがって `backtest.py` の `[diff] |FIR_max - FFT|` は、**イベントが窓に収まった地震
波形でしか意味を持たない**。300秒の静穏記録に対する「全体の震度」は気象庁の定義には
存在しないので、静穏データで diff を見ても検算にならない。

数値照合をやるなら合成波か実イベントの波形を使う:

```bash
python tools/gen_synthetic.py --kind quake --amp 20 --seconds 90 | python tools/backtest.py -
```

合成地震（amp = 5 / 20 / 100 gal）では **FFT版とFIR版の震度は完全一致する**
（`tools/tests/test_jismo.py::test_fft_and_fir_intensities_agree_on_quake`）。

## 2. 本当の問題: ドリフト × 巡回畳み込みで窓の端が暴れる

`jma_fft._apply_filter` は FFT で `Y(f)` を掛け `irfft` で戻す＝**巡回畳み込み**である。
記録の終端と始端が繋がったものとして扱われるので、そこに段差があるとフィルタの
長い応答が端でリンギングする。

`Y(f)` は `f=0` でちょうど 0 なので**直流（重力1g）は落ちる**。落ちないのは**傾き**だ。
センサの傾斜変化や熱ドリフトは記録内で加速度がランプ状に動く形になり、
これが繋ぎ目の段差になる。

実機データ（ADXL355・据え付け前・電源投入8分後の静穏300秒。x軸が300秒で 8.3 gal ドリフト）:

| 前処理 | 計測震度 | a0 | peak |
|---|---|---|---|
| 生のまま（修正前の挙動） | **2.13** | 3.92 gal | 4.15 gal |
| 平均を引く | 2.13 | 3.92 gal | — |
| **線形トレンドを引く** | **-0.62** | 0.17 gal | 0.28 gal |
| 前後5秒を捨てる | -0.20 | 0.27 gal | — |

平均を引いても変わらないことが決め手である。**直流ではなく傾きが犯人**だと分かる。

暴れが窓の端に張り付いていることも確認した。120秒窓を30秒ずつずらして評価すると:

```
窓0 t=  0-120s  peak(全体)=2.220gal   peak(端5s除く)=0.274gal
窓3 t= 90-210s  peak(全体)=1.536gal   peak(端5s除く)=0.171gal
窓6 t=180-300s  peak(全体)=1.337gal   peak(端5s除く)=0.230gal
```

閾値超えのサンプル位置は毎回「先頭 0.0秒」と「末尾 120.0秒」だった。記録中の特定の
時刻ではなく**窓の端そのもの**に出る＝データではなく変換の副産物である。

なお **IIS3DHHC の既存キャプチャ（`tools/rest.csv`）はこの影響をほぼ受けていない**
（震度 0.728 → 修正後 0.728）。あの記録のドリフトは60秒で 0.17 gal しかない。
`rest.csv` の震度が高め（0.73）なのは机上の生活振動が実際に入っているためで、
端の暴れとは別の話。**ドリフトの大きい記録でのみ顕在化する問題**だった。

## 3. 本番への影響

`detect` Lambda は 120秒窓（`NAMZ_DETECT_WINDOW_S`）をバッチ毎（30秒毎）に
`jma_fft` へ渡していた。デトレンドも端の切り捨ても無かったので、この経路をそのまま踏む。

- **誤検知は発生しなかった**（静穏300秒 → 7窓すべて未検知）。「閾値以上が2秒継続」
  （`HOLD_SECONDS`）の条件に救われている。端の暴れは先頭と末尾に分かれて出るので
  1箇所あたり1秒強しか続かない。
- **危ないのは値の水増しの方**。`peak_gal` は実体の約8倍（2.22 vs 0.27 gal）になり、
  `max_intensity` も膨れる。端の暴れ 2.2 gal は震度 1.5 相当で、これは
  `NAMZ_NOTIFY_CONFIRM_MIN`（Slack確定通知の下限・既定 1.5）と同じ高さにある。
  弱いイベントが水増しで通知閾値を跨ぎうる。

実害が出る前に見つかった（本番稼働中に実地震はまだ来ていない）ので、過去イベントの
再計算は行っていない。

## 4. 入れた修正

1. **`jma_fft.detrend()` を追加し、`_apply_filter` の先頭で必ず掛ける。**
   線形トレンド（直流＋傾き）を除いてからフィルタする。気象庁の手法が想定するのは
   「静止に始まり静止に終わる地震記録」で元の定義にこの処理は無いが、こちらは連続
   ストリームを任意の位置で切った窓を渡している。ドリフトは地動ではないので、
   除いてから掛ける方が定義に忠実である。
2. **`detect_core.core_slice()` で窓の端 5秒を評価から外す**（`EDGE_GUARD_SECONDS`）。
   デトレンドで大半は消えるが、窓の切れ目に本物の過渡が跨いだ場合は残るため。
   窓は120秒・30秒毎の評価で重なりが厚いので、端を落としても取りこぼさない
   （次の窓では同じ時刻が内側に来る）。
3. **`jma_fft.intensity_from_composite()` を分離。** `detect_core` と
   `tools/promote_event.py` が同じ合成波形（端を落としたもの）から震度を出すようにした。
   ついでに、どちらも同じ波形にフィルタを二度掛けていたのをやめた。手動昇格と自動確定で
   同じ波形から違う震度が出ないようにするためでもある。

修正後、同じ静穏300秒は **震度 -0.77 / a0 0.139gal / peak 0.276gal**。合成地震
（5/20/100 gal）の震度は**修正前後で変化なし**、`tools/rest.csv` も変化なし。

## 5. 残る限界

- デトレンドは**線形**のみ。温度変化が曲線的に効く区間では取り切れない。実運用で
  問題になったら多項式次数を上げるより、断熱と据え付け（[adxl355.md](adxl355.md) §7）で
  元を断つ方が筋がよい。
- 端5秒のガードは `detect` と `promote_event` の経路にのみ入っている。`jma_fft` を
  直接呼ぶ解析スクリプト（`backtest.py` 等）は記録全体を評価する。手で解析する時は
  「端が汚れている可能性」を意識すること。

## 6. 再現

```bash
# 静穏キャプチャ（ADXL355なら --sensor adxl355 必須。既定は無い）
python tools/capture_serial.py --sensor adxl355 --port /dev/tty.usbserial-XXXX \
    --seconds 300 > rest.csv
python tools/backtest.py rest.csv      # 静穏では diff を見ても意味が無い（§1）
python tools/spectrum.py rest.csv      # ドリフト量は 0-1Hz のパワー割合に出る
```

回帰テスト:

```bash
pytest tools/tests/test_jismo.py -k "drift or agree"
pytest lambda/tests/test_detect_core.py -k "drift"
```
