# ADXL355 導入作戦

device 0001（IIS3DHHC）のノイズフロアがセンサ律速だと [noise.md](noise.md) で確定したため、
ADXL355 機を追加する。2026-07-28 時点の検討結果。

**進捗**: 2026-08-02 に基板着荷。ファーム側（§5）実装済み、配線して ID・重力1g・
100Hz 出力まで確認済み。設置材料は 2026-08-03 に調達済み（§7.3.1）、同日夜にコンクリート
ブロックへ固定・起立。2026-08-05、固定後一晩（静穏区間9時間）のノイズ測定を実施
（[noise.md の測定ログ](noise.md#2026-08-05-コンクリートブロック固定後一晩静穏区間9時間)）。
**§6 判定: 水平x/y軸は合格ライン到達（ASD 16前後・PSD平坦）、z軸は未達（24–28 vs 14–17）**。
震度ベースラインも -0.86 で目標 -1.0〜-1.1 に届かず。z軸の残差は §7.4 未実施の断熱が主因の
疑いがあり、残るは断熱の実施と再測定。同時刻の device 1（ブレッドボード直挿しのまま）との
比較では震度ベースラインが +0.36階級改善（[noise.mdの比較](noise.md#device-1iis3dhhcブレッドボード直挿しとの同時刻比較)）。
ただしセンサ交換と設置改善の効果が未分離。**device 1 も同じアルミ板＋コンクリブロック方式へ
固定する予定**があり、移行後に同一設置での再比較を行う。

## 1. 動機と期待値

[noise.md](noise.md) の実測: 静穏時PSDは全帯域で平坦（白色）＝センサ/電子系の熱雑音。
環境振動でも量子化（~3 µg/√Hz）でもない。よってセンサを換えれば素直にフロアが下がる。

`I = 2·log10(a0) + 0.94` に入れた見込み:

| | 現行 IIS3DHHC | ADXL355 見込み | 他機実測（東京） |
|---|---|---|---|
| ノイズ密度（データシート） | 45 µg/√Hz | 22.5–25 µg/√Hz | — |
| in-band ASD（実効） | 25–30 µg/√Hz | **14–17 µg/√Hz** | — |
| broadband RMS（0–50Hz） | 0.18 gal | **≈ 0.10 gal** | 0.085 gal |
| 60秒窓 震度ベースライン | -0.55 | **≈ -1.05** | -1.2 |

`2·log10(25/45)` = **-0.5階級**。他機実測 -1.2 と誤差の範囲で整合する。

これで解ける見込みのもの:

- **令和8年熊本地震（~870km）**: 現行は連続震度で完全埋没。東京ADXL355では +1.2階級の
  明瞭なバンプ。湯沢でも同様に出るはず。
- **20:53 福島県沖 M4.0（268km）**: 現行 STA/LTA で probable。背景が半減すれば definite 圏。

## 2. 価格と代案（検討済み・却下）

実売 **¥8,156**（`EVAL-ADXL355-PMDZ`・Digikey JP 税抜。§4.1。当初想定6600円は外れたが
1万円ほどではない）。下記の代案より筋がよい。

- **IIS3DHHC を3個並べて平均**（7260円）: √3 でフロアは 0.104 gal、ADXL355 単体とほぼ同等。
  しかし**熱ドリフトと傾斜は3個で相関するので平均で消えない** → z軸 <0.2Hz の突出
  （90–130 µg/√Hz）は残る。配線もSPIも3倍。**却下**。
- **速度計/広帯域地震計**: <0.2Hz の遠地表面波を狙うなら本来これ。桁違いに高い。将来課題。

## 3. 方針: 置き換えず2台目にする

現行 IIS3DHHC 機（device 0001・湯沢）はそのまま残し、**別 device_id の2台目**として組む。

- `namazu-devices` / watchdog / api は最初から複数デバイス前提。ESP32をもう1枚用意して
  `kDeviceId` を変えるだけで、欠測監視も一覧もそのまま2台を扱う。
- **比較フェーズ**: 同じ場所に数日並べる（**同じ架台に並べて貼る**。§7.4）。同一イベントの
  震度を直接比較でき、[noise.md](noise.md) の見込み値を実測に置き換えられる。
- **運用フェーズ**: 比較後は別の部屋／別拠点へ離す。**同時刻に両方で立てば地震、片方だけなら
  家の中の何か**。`kAlertHoldSeconds` の類より本質的な誤検知の弁別軸になる。
- 同一ボードに2センサ相乗りはCSを分ければ電気的には可能だが、Batch/Uploader が1系統前提。
  割に合わないので**やらない**。

## 4. ハード

素チップはLGAで手はんだ不可級。**ブレイクアウト基板を買う**。

### 4.1 ボード選定: `EVAL-ADXL355-PMDZ` を採る

ADI 純正の候補は2つ。価格は Digikey JP 税抜（2026-07-28 時点）:

| | EVAL-ADXL355-PMDZ | EVAL-ADXL355Z |
|---|---|---|
| 価格 | **¥8,156** | ¥9,675 |
| 形状 | 2.5cm角 Pmod | 0.8in角 ブレークアウト |
| ヘッダ | **2x6 オス実装済み** | **ビアのみ**（6ピン×2を自前はんだ付け） |
| I/F | extended SPI 専用 | SPI / I2C（ASELで選択） |
| マウントホール | 製品写真・wiki とも見当たらない | 四隅に4つ |
| ドライバ資産 | ADI no-OS / Linux IIO / pyadi-iio | 無し（素のブレークアウト） |

**PMDZ を採る。** 安く、ヘッダが実装済みで、参照実装がある。

- 「2列ヘッダなのでブレッドボードに挿しにくい」は**問題にならない**。Pmod extended SPI は
  1列目だけで完結する: `1=CS / 2=MOSI / 3=MISO / 4=SCLK / 5=DGND / 6=VDD(3.3V)`
  （2列目は `7=INT1 / 8=NC / 9=INT2 / 10=DRDY / 11=DGND / 12=VDD`）。
  メス-メスジャンパ6本で ESP32 に直結すれば足りる。ブレッドボードを経由する必要がない。
  そもそも §7 でセンサを本体から離すので、**12ピンをリボンケーブル1本で引けるこの形は
  むしろ利点**（ジャンパ6本束より機械的に抜けない）。
- 電源は host の 3.3V 直結（Pmod 規定で 100mA まで供給される）。ESP32 とレベルも一致し
  変換不要。デカップリングは基板任せ。
- 355Z を選ぶ唯一の理由はネジ止め穴だが、§7 の通り**賃貸ではそもそもネジを使えない**ので
  決定要因にならない。加えて 355Z は逆極性保護なし・内部LDO出力（V1P8ANA/V1P8DIG）が
  ヘッダに露出しており、誤配線で殺しやすい。
- **SDP 母板（`EVAL-SDP-CB1Z` 等）は不要**。PMDZ も 355Z も外部ホストから直接叩ける。
  SDP が要るのは PC の ADI 評価ソフトで動かす `EVAL-ADXL35x-SDP` キットの話で別物。

出典: [PMDZ User Guide (ADI wiki)](https://wiki.analog.com/resources/eval/user-guides/circuits-from-the-lab/eval-adxl355-pmdz) /
[UG-1030 (355Z)](https://www.analog.com/media/en/technical-documentation/user-guides/EVAL-ADXL354-355-UG-1030.pdf)

### 4.2 配線

- 電源 2.25–3.6V。3V3直結でよい。
- SPIピンは現行と同じ割り当て（[config.h](../firmware/src/config.h)）。CS だけ別にした。
  無印 WROOM-32 DevKit を使うなら 18/19/23/5 に戻す。
- Pmod 2列目（INT1/INT2/DRDY）は結線しない（§8）。

TTGO T-Display の場合の実配線（Pmod 1列目のみ）:

| Pmod J1 | 信号 | ESP32 |
|---|---|---|
| 1 | CS | GPIO32 (`kPinCsAdxl355`) |
| 2 | MOSI | GPIO26 (`kPinMosi`) |
| 3 | MISO | GPIO27 (`kPinMiso`) |
| 4 | SCLK | GPIO25 (`kPinSck`) |
| 5 | DGND | GND |
| 6 | VDD | 3V3 |

CS が IIS3DHHC(GPIO33) と別なので、**比較フェーズでは両方を同じバスに挿したまま
ファームだけ焼き分けられる**。

## 5. ファーム実装

### 5.1 ドライバ `firmware/lib/Adxl355/`

[AccelSensor](../firmware/lib/AccelSensor/AccelSensor.h) の5メソッドを実装するだけ。
`Iis3dhhc` との差分で転びやすい点:

- **SPIは mode 0**（IIS3DHHCは mode 3）。最大10MHz。`SPISettings` はデバイス毎なので同居可。
- **R/Wビットの位置が逆**。ADXL355 は `(reg << 1) | 1` で読み。IIS3DHHC のMSB流儀ではない。
- ID: `DEVID_AD(0x00)=0xAD` / `DEVID_MST(0x01)=0x1D` / `PARTID(0x02)=0xED`。
- データは `XDATA3(0x08)` から9バイト連続読み。各軸3バイトに20bit左詰め:

  ```cpp
  int32_t v = (b0 << 12) | (b1 << 4) | (b2 >> 4);
  if (v & 0x80000) v -= 0x100000;   // 20bit符号拡張
  ```

- `RANGE(0x2C) = 0x01` → **±2.048g**。最小レンジが最小ノイズ。3.9 µg/LSB。
  フルスケール 2009 gal なので震度7でも余る。
- `FILTER(0x28)`: **HPF_CORNER は必ず 0（OFF）**。低域処理は気象庁法のFIRの仕事であり、
  センサ側で位相をいじられると `tools/backtest.py` の数値照合が壊れる。
- `ODR_LPF` は **2000Hz（内部LPF -3dB = 500Hz）**。内部ODRは自走でESP32の1msタイマと
  非同期なので、読み周期の2倍にしておけば毎回新しいサンプルが取れる（重複読みなし）。
  厳密にやるなら DRDY割り込みか `STATUS` の DATA_RDY を見る。**FIFO(96サンプル)は使わない**
  （現行のesp_timer駆動アーキテクチャを崩さない）。
- `POWER_CTL(0x2D)`: measurement mode、温度センサON。

### 5.1.1 SPI読み取り不良で3軸すべて0になる（実機で観測・データ汚染だけ対処済み）

2026-08-03 22:06〜22:27 JST、据え付け直後の2号機で断続的に3軸すべてが厳密に0になる
区間が出た（S3の生データで確認。バッチ内のゼロ比率が22→141→460→1342→1500/1500と
数十秒かけて悪化し、また数十秒かけて回復する“じわじわ”したパターン。加えて数分の
完全欠測ギャップも別途あり、こちらは再起動/再接続と見られる）。配線を触っていないのに
直ったように見えたのはこのため——実際には接触が戻っただけで、原因側は未解決。

原因の一端は `Adxl355::read()` が**SPI読み出しの成否を検証せず常に `true` を
返していた**こと。CS/MISO の接触が怪しくなると読み出しバッファが0で埋まり、
それがそのまま「有効なサンプル」としてオーバーサンプリング平均に混入していた。
重力がある限り3軸が同時に厳密0になることは物理的にないので、この検知に使える。

**やったこと（データ汚染の防止のみ）**: `Adxl355::read()` で3軸すべて0の読みを
失敗（`false`）扱いにし、そのサンプルだけ捨てるようにした
（`firmware/src/main.cpp` の `if (!gSensor.read(rd)) continue;` が既にこの契約で
動くので変更不要）。これで偽の0gサンプルが震度計算やノイズ測定に混入することは
防げるが、**配線側の不具合そのものは直っていない**。全読みが失敗し続ける区間は
単にサンプルが欠けるだけで、5分未満の欠測は watchdog（`offline_after_s=300`）
にも引っかからず、誰にも気づかれない。

**やっていないこと**: 検知回数のクラウドへの通知（温度トレーラーと同じ仕組みに
乗せられる）。再発を見てから判断する。まず疑うべきは配線（アルミ板に貼った
直後のケーブル取り回し、§7.3のサービスループ）。`Iis3dhhc::read()` にも同じ
検証漏れがあるが、今のところ発生報告なし。

**別件との切り分け**: device2では別途、約36〜37秒の完全なデータ欠落が不規則に
繰り返し発生する問題も見つかったが、原因はSPI配線ではなく`uploaderTask`のTASK_WDT
（送信側のTLSハンドシェイク待ちで停止）と確定している。詳細・現在の対策状況は
[design.md「送信の信頼性」](design.md#送信の信頼性)参照。

### 5.2 サンプルのビット幅（int32 か `>>3` か）

ADXL355 の生値（3.9 µg/LSB）を素で int16 に入れると **±0.128g = 125 gal（震度5弱相当）で
クリップ**する。どちらかを選ぶ。**int32 が本命**。

| 案 | scale_mg_per_lsb | クリップ | 量子化ASD | バッチ長 | 作業 |
|---|---|---|---|---|---|
| **int32（本命）** | 0.00390625 | 2009 gal | 無視可 | 36KB/30s | Batch を12B/int32対応 |
| `>>3`（逃げ道） | 0.03125 | 1004 gal（震度6.9） | 1.3 µg/√Hz | 18KB/30s | `scaleMgPerLsb()` だけ |

- `sample_format=1`（int32）は **[wire.py](../lambda/common/wire.py#L60-L65) が既に対応済み・
  クラウド側の変更はゼロ**。ヘッダが感度もビット幅も運ぶ設計のため。
- 要る改修は firmware だけ: 当時の `Batch` は `kSampleBytes=6`・`addSample(int16_t...)` の
  int16 固定だった。12B/int32 に対応させる。
- **RAM注意**: 36KB × `kMaxRamBatches=6` = **216KB**。実機のヒープで要確認。
  足りなければ `kMaxRamBatches` を落とすか、`>>3` に逃げる。
- どちらでも丸め（量子化）は律速にならない。間引き後RMSは int32 で ≈26 LSB、
  `>>3` でも ≈3.3 LSB あり、丸めの 0.29 LSB を大きく上回る。
  **int32 を選ぶ理由はダイナミックレンジであって量子化ではない。**

### 5.3 却下した案

- **10平均の合計値を int32 にそのまま載せて scale を1/10にする**: 端数を捨てずに済むが、
  現行の丸めが押し上げているフロアは 0.7%（震度0.006階級）しかない。**利得ゼロ・却下**。
  （`accX / kOversample` のゼロ方向切り捨ても同様に無害。DCはFIRが落とす）

## 6. 検証（[design.md](design.md#L110-L112) の不変条件）

この順に通すまで実戦投入しない。

0. `pio run -e adxl355-sensortest -t upload && pio device monitor` で
   `[sensor] ADXL355 ready` が出るか（出なければ配線かCSを疑う）
1. `python tools/capture_serial.py --sensor adxl355 --port ... > cap.csv` でシリアルキャプチャ
2. `python tools/backtest.py cap.csv` で `tools/jismo` と**数値照合**
3. 静穏区間を数時間流し、[noise.md](noise.md) と同じ手順で ASD を出す

### 受け入れ基準

| 項目 | 合格ライン |
|---|---|
| in-band ASD（0.5–40Hz） | 14–17 µg/√Hz |
| broadband RMS（0–50Hz） | ≈ 0.10 gal |
| 60秒窓 震度ベースライン | -1.0 〜 -1.1 |
| PSD形状 | 平坦（白色）のまま |

### 判定ルール

- **ベースラインが -1.0 に届かない**、かつ PSD が低周波へ立ち上がる形に変わった
  → センサではなく**環境振動が顔を出した**。設置改善（§7）へ。
- **z軸 <0.2Hz の突出（現行 90–130 µg/√Hz）が改善しない**
  → センサの1/fではなく**架台の熱ドリフト/傾斜が主因**と確定。断熱・剛結へ。
  改善するなら `--axes xy` の回避策を外せる。
- `--axes xy` は当面そのまま残す。**実測で判定するまで z を信じも捨てもしない。**

## 7. 設置（優先順位が入れ替わる点に注意）

[noise.md:62](noise.md#L62) は「設置改善は現機材では二次的（フロアが白色＝センサ）」と
書いているが、**ADXL355 を入れた瞬間に一次的へ昇格する**。フロアが 0.18 → 0.10 gal に
落ちれば、いま熱雑音に隠れている生活振動・空調が顔を出しうる。

### 7.1 現状の問題: センサをブレッドボードに直挿ししている

device 0001 はセンサ基板をブレッドボードに直挿しし、ブレッドボードは机に置いてあるだけ。
この状態で測っているのは床ではなく**ブレッドボードの振動**である。ジャンパのバネで基板が浮く。
[noise.md](noise.md) の数値にはこの寄与が混ざっている（ただし §1 の通りフロアは白色なので
主因はセンサ。設置寄与が顔を出すのはフロアが下がってからである）。

**固定すべきはセンサだけ。ESP32 とディスプレイはブレッドボードのままでよい。**

```
[床] ==剛結== [センサ基板] --ケーブル数十cm-- [ブレッドボード: ESP32 + 表示]
```

SPI なので 30cm 程度の引き回しは問題ない（100Hz 測定・SCLK 数MHz）。

### 7.2 コンクリート平板方式（賃貸で剛結を諦めない）

**賃貸なので建物に穴も粘着剤も使えない。** ネジ止めの代わりに慣性を借りる。

コンクリート平板（ホームセンターの 300×300×60mm・10kg 前後・数百円）かピンコロ石、
石定盤を床に直置きし、センサをその上面に貼る。平板は十分に重いので床と一体で動く
（硬い床の上での接触剛性は高く、この質量でも共振は数百Hz以上に飛ぶ）。粘着剤が触れるのは
**自分の所有物である平板だけ**で、建物には一切触れない。退去時は平板ごと処分する。

置き場所:

- **硬い床に直置き**（フローリング・CF・土間）。
- **カーペットと畳の上は不可**。バネの上に重りを載せる形になり、質量-バネ系の共振が数Hz
  ＝計測震度の関心帯域に山を作る。カーペットしかない部屋では重量方式は逆効果で、
  軽く薄い基板を床材に直接貼る方向に切り替える。
- **部屋の中央より壁際・柱際**。床のたわみが小さく、床自体の固有振動の増幅を拾いにくい。
  押入れの床などは条件がよい。

### 7.3 貼り方

PMDZ にマウントホールが無いので接着になる。間にアルミ板を1枚噛ませる:

```
[コンクリート平板] --VHB-- [アルミ板 2〜3mm] --VHB-- [PMDZ 裏面]
```

- 板を挟むのは、剥がすときに PCB を直接引っ張らないため。VHB は硬いので直貼りを無理に
  剥がすと部品や端子を持っていく。板が薄ければ剛性は落ちない。
- 裏面の背の高い部品を実物で確認し、干渉するなら板を逃がすか部品のない領域だけに貼る。
- **ホットボンド禁止**（温度で軟化してオフセットがドリフトする）。
  **軟らかいスポンジ両面テープ禁止**（剛結になっていない）。
- ケーブルは平板か床に一箇所留め、センサ側にサービスループ（たるみ）を作る。
  ケーブルの張力はそのまま低周波ノイズになる。

### 7.3.1 調達した実材料（2026-08-03）

上図の VHB×2 から、**下側だけエポキシに変えた**。土台は自分の所有物で恒久固定して
構わないので、VHB より剛なエポキシにする。基板側は回収できるようテープに残す。

```
[コンクリートブロック 横置き・実面上] --エポキシ90分-- [金属板 3mm] --アクリルフォーム両面テープ-- [PMDZ 裏面]
```

- **土台**: コンクリートブロック（隅用）。§7.2 の平板の代わり。**横置き（広いフェイスシェル面を
  上下）** にすると上面が中実の平面になり、空洞コアが横を向くのでコア上の薄殻が鳴らない。
  硬い床に直置きし、ガタつきはシムで殺す。カーペット・畳の上は不可（§7.2）。
- **中間板**: HIKARI HA8013（金属板 厚3mm・100×200mm）。§7.3 のアルミ板の役。
- **恒久側の接着**: ボンド Eセット（エポキシ・90分硬化型）。**ブロック↔金属板のみ**。
  90分型は5分型より最終強度・剛性が出る。**PMDZ には塗らない**（塗ると基板を回収不能にする）。
- **可剥がし側の接着**: 3M スコッチ プレミアゴールド スーパー多用途 KPS-12
  （アクリルフォーム基材・12mm×1.5m）。金属板↔PMDZ 裏面。アクリルフォームは硬く、
  §7.3 が禁じる「軟らかいスポンジ」ではない（VHB相当）。触れるのは平滑面（金属・PCB）
  のみなので粗面用（KPR-12R）は不要。貼る前に爪で沈まないことだけ確認する。

### 7.4 残り

- 水平出し（水準器）。軸を N/E/Z で揃える。傾くと重力が水平2軸に漏れてオフセットになる。
  **一度固定したら動かさない**（オフセット校正がやり直しになる）。
- 気流と温度勾配を切る覆い（**断熱**）。覆いはセンサに触れさせず平板側に立てる。
- 動線・空調・冷蔵庫・直射日光から離す。[design.md:83](design.md#L83) の
  「候補場所ごとに数日置いて実測」を、**ADXL355でこそやる**。
- **§3 の比較フェーズでは IIS3DHHC と ADXL355 を同じ平板に並べて貼る。** 同一入力を同時に
  測れるので、§1 の見込み値を推定でなく実測の差分として出せる。
- 設置を直したら [noise.md](noise.md) の ASD は変わる。**再測定して更新する。**

## 8. やらないこと（今回のスコープ外）

- **FIFO / DRDY割り込み駆動**: 現行のesp_timer駆動で足りる。必要になってから。
- ~~**温度の送信**~~ → **実装した**。wire format v2 の TLV トレイラーで生値を送る
  （[wire_format.md](wire_format.md#トレイラー-v2省略可)）。据え付けのドリフトが熱由来か
  判定するために要る。震度算出には使わない（FIRが低域を落とすので実害はない）。
- **<0.2Hz の遠地表面波**: `a ∝ f²·D` により加速度計では原理的に不利。ADXL355でも変わらない。
  狙うなら速度計。
- **IIS3DHHC 機の撤去**: 残す（§3）。
